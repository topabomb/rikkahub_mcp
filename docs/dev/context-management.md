## 结论

Measix Pilot 适配引入上游的“阶梯式上下文裁剪”，但不把它定义为模型上下文窗口管理，也不
原样采用上游参数和边界算法：

1. 默认不自动裁剪；用户在 Assistant 设置中显式开启。
2. 开启时默认 80 条、最低 40 条、最高 512 条，保留比例为 50%。
3. 裁剪点只按台阶移动，并回退到完整 USER 轮次；请求裁剪不改写持久化会话。
4. 手动“压缩上下文”继续承担语义摘要职责，切点和分块同样对齐完整 USER 轮次。
5. 当前不实现自动 token 摘要或“按模型窗口自动裁剪”。在模型窗口元数据、请求前 token
   计量和可审计摘要尚未建立前，这种自动化会制造不可见的信息丢失。

因此，当前是“两层、显式”的方案：

| 层次 | 目的 | 是否改写会话 | 默认行为 |
|------|------|--------------|----------|
| 请求级阶梯裁剪 | 控制发送历史长度并减少相邻请求的缓存前缀漂移 | 否 | 关闭 |
| 用户触发语义压缩 | 用摘要替换较早历史，长期降低上下文体积 | 是 | 仅用户确认后执行 |

## 为什么不恢复旧滑动窗口

旧 `contextMessageSize` 每增加一条消息就把窗口前移一条。即使窗口内绝大部分内容相同，请求
的第一个历史消息也持续变化，Provider 无法复用从请求开头建立的提示缓存。

阶梯策略在越过阈值时一次前移较大步幅，随后多轮只在尾部追加消息。它不能避免裁剪发生时的
缓存失效，但能显著降低失效频率，适合作为默认关闭的高级控制。

## 对上游 `2d61ba9` 的审查

### 合理部分

- 使用独立的新字段 `contextMessageLimit`，不让旧 `contextMessageSize` 自动恢复新行为；
- `0` 保持无限制，旧配置和现有用户默认行为不变；
- 锚点由消息数量确定，无需在 `Conversation` 中持久化额外 anchor；
- 50% 滞回在“保留历史”和“减少锚点移动”之间取了简单、可解释的平衡；
- 裁剪在 Input Transformer 之前执行，避免对必然丢弃的长历史反复做 OCR、文档转换和模板处理；
- 有独立单元测试覆盖关闭、越界、台阶稳定和工具边界。

### 不原样引入的部分

1. **缓存命中率估算偏乐观**  
   上游按“每次请求增加一条消息”估算，称 `limit=40` 约 95%。本项目普通一轮通常新增
   USER、ASSISTANT 两条消息；40 条阈值约每 10 次请求移动一次锚点，理想值更接近 90%，
   80 条才接近 95%。因此本地采用最低 40、启用默认 80。

2. **安全边界与真实消息结构不一致**  
   上游通过“已执行 Tool 向前寻找任意未执行 Tool”回溯，既没有按 `toolCallId` 配对，
   也没有保证普通 ASSISTANT 回复保留其 USER 问题。本项目工具调用和结果本来就在同一个
   `UIMessagePart.Tool` 中；最可靠的边界是最近的 USER 消息。本地让自动裁剪、手动压缩保留
   和压缩分块共用 `findUserTurnStart()`。

3. **“上限”不是 token 窗口**  
   上游 UI 容易让用户把消息条数理解为模型容量。本地改成显式开关，并在文案中说明这是
   消息阈值；非零值只用警示色，不作为错误或阻断状态。

4. **低值与跨版本输入需要归一化**  
   本地持久化仍保存原始字段，但请求和 UI 统一通过 `effectiveContextMessageLimit()` 归一化：
   非正数关闭，1～39 按 40，超过 512 按 512。导入上游或异常备份不会绕过产品约束。

5. **同一上下文事实源**  
   `GenerationHandler` 先得到 `contextMessages`，随后 Tool system prompt 和实际请求都使用
   这份列表，避免未来某个工具按消息生成提示时看到未裁剪历史。

## 缓存利用率边界

提示缓存能否命中不仅取决于裁剪锚点，还取决于从请求开头开始的所有内容是否一致。

当前有利条件：

- `TemplateTransformer` 使用每条消息的 `createdAt`，不会用当前时间重写历史；
- `TimeReminderTransformer` 也由持久化消息时间推导；
- 阶梯内的历史起点稳定；
- 工具结果只改变当前尾部消息，不改写更早前缀。

会合理导致缓存变化的条件：

- Assistant System、会话 System、Mode Injection 或 Workspace 环境变化；
- Memory 被模型工具新增、修改或删除；
- 启用的 Tools、MCP 工具 schema、模型或 Provider 发生变化；
- 到达下一裁剪台阶；
- Provider 自身的缓存最小 token 数、TTL 或路由变化。

因此 UI 和文档只描述“减少缓存失效频率”，不承诺实际命中率。实际命中仍以响应中的
`cachedTokens` 为准。

## 上下文窗口与 token 预算

当前 `Model` 没有可信的 `contextWindowTokens`：

- 自定义模型名称无法可靠映射容量；
- 同名模型可能被代理服务配置为不同窗口；
- OpenAI、Claude、Google 及兼容接口的 tokenizer 不统一；
- 文档、OCR、图片、Tool schema 和注入是在 Input Transformer/Provider 序列化阶段扩展的；
- Provider 返回的 `promptTokens` 是请求完成后的观测值，不能单独作为当前请求的预检。

所以消息阈值不能替代如下预算：

```text
可用输入预算
  = 模型上下文窗口
  - 预留输出 token
  - System / Memory / Tool schema 固定开销
  - 安全余量
```

`Assistant.maxTokens` 只控制预留输出的一部分，不能代表模型窗口。

### 后续实现前置条件

只有同时具备以下能力，才应增加自动 token 管理：

1. `Model` 支持“注册表默认值 + 用户覆盖”的窗口元数据，并记录来源；
2. Provider 层提供请求序列化后的 token 估算接口，未知模型允许明确降级为保守估算；
3. 预算覆盖 System、Memory、Tools、Transformers、多模态和输出预留；
4. 超预算时先给出可解释的裁剪/压缩预览；
5. 自动摘要必须显式 opt-in，保存摘要范围、生成模型和时间，且不拆散 USER/工具轮次；
6. 请求失败仍保留原始会话，不能以恢复发送为由静默覆盖历史。

在此之前，最佳降级顺序是：

1. 默认发送完整历史；
2. 用户有成本或历史长度需求时开启请求级阶梯裁剪；
3. 长期会话由用户显式执行语义压缩；
4. Provider 报窗口错误时保留原始错误，并引导用户调高裁剪强度或执行压缩。

## 显式压缩的当前边界

`ChatService.compressConversation()` 已有的目标 token 是提示模型生成多长的摘要，不是本地硬
token 校验。此次只修复可确定的结构问题：

- “保留最近消息”的切点回退到 USER；
- 256 条分块的中点优先回退到 USER；
- UI 明确说明保留数量是最低值、摘要会替换旧历史且不可撤销。

本次不把分块从消息数擅自改成固定字符数。固定字符同样不是 token，在中文、代码、JSON、
图片和不同 tokenizer 下偏差很大；它会把一个不准确的启发式替换成另一个不准确的启发式。
真正改造应与模型窗口元数据和 Provider token 估算一起完成。

## 持久化与兼容

- `Assistant.contextMessageLimit: Int = 0` 是带默认值的新 JSON 字段，无 Room schema 变化；
- 旧 `contextMessageSize` 继续由 `ignoreUnknownKeys` 忽略，不会静默开启新策略；
- 请求级裁剪不写回 `Conversation`；
- 语义压缩保持原有的显式持久化行为；
- 导入的异常非零阈值在使用时归一化到 40～512。

## 验证要求

- `limitContext()`：关闭、阈值内、跨台阶、同台阶锚点稳定、完整 USER 轮次、后缀一致；
- `findUserTurnStart()`：普通问答和工具消息边界；
- `Assistant`：默认值、低/高值归一化、旧字段不会启用新策略；
- 五语言资源键一致且无重复；
- `:ai:test`、`:app:testDebugUnitTest`、Lint、Debug/Release 构建通过。
