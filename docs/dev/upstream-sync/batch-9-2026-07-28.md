### 3.18 `2d61ba95` — feat(assistant): 上下文限制改为阶梯式截断，保留提示词缓存

| 项目 | 内容 |
|------|------|
| **类别** | 功能增强（cache/context） |
| **优先级** | P1 |
| **判定** | ✅ 适配引入 |

**上游方案**：

- 新增 `contextMessageLimit`，`0` 表示不限制；
- 超过阈值时按 50% 保留比例一次前移一个大台阶，台阶内追加消息不移动请求前缀；
- 在 `GenerationHandler` 构建请求时、Input Transformers 之前裁剪；
- 上游 UI 允许 0 或不低于 20 的滑块值；
- 通过回溯未执行/已执行 Tool 避免从半截工具调用开始；
- 新增 10 组 `MessageTest` 并补充上游生成链路文档。

**合理性判断**：

- 阶梯滞回解决了旧滑动窗口“每轮移动一条、持续破坏缓存前缀”的核心问题；
- 默认 `0` 不改变现有用户行为，新字段不复用旧字段，持久化设计合理；
- 但消息条数不能代表模型 token 窗口，不能把此功能宣传为窗口溢出保护；
- 上游缓存估算按每请求增加一条消息计算，而本项目普通一轮新增 USER、ASSISTANT 两条：
  阈值 40 理想上约 90%，阈值 80 才约 95%；
- 上游工具边界按“任意未执行 Tool”回溯，未按 `toolCallId`，也不能保证普通 ASSISTANT
  回复保留对应问题；本项目工具调用和结果本来就在同一个 `UIMessage`，应直接对齐 USER 轮次。

**本地适配**：

- 保留 50% 阶梯策略，但统一通过 `findUserTurnStart()` 回退到完整 USER 轮次；
- Assistant 设置改为显式开关：默认关闭，开启默认 80，范围 40～512，非阻断警示色；
- `effectiveContextMessageLimit()` 统一归一化导入或异常持久化值；
- Tool system prompt 与 Provider 请求使用同一份已裁剪 `contextMessages`；
- 手动语义压缩的“保留最近消息”和 256 条分块也复用 USER 边界；
- 五语言文案明确“消息数不是 token 上限”，并修正压缩不可撤销提示；
- 同步并按本地代码重写
  [`docs/references/chat-generation-pipeline.md`](../../references/chat-generation-pipeline.md)，
  决策详见 [`docs/dev/context-management.md`](../context-management.md)。

**测试**：

- `MessageTest` 覆盖关闭、阈值内、台阶稳定、完整 USER 轮次和后缀性质；
- `AssistantContextLimitTest` 覆盖默认/越界归一化及旧 `contextMessageSize` 不会启用新策略。
