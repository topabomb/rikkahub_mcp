- `McpStatus.Error(message: String)` 仅有 message，无 detail

**判定**：✅ **选择性引入**（不引入整体重构，仅引入 Error.detail + Error.from() + UI 展示 + McpConnectionKey）

**深度调研结论**：

本地 McpManager（batch-3 0.0.7）与上游重构后的架构对比：

| 方面 | 上游重构后 | 本地 batch-3 | 差异分析 |
|------|------|------|------|
| 架构 | McpManager(141行) + McpSessionRegistry(460行) + McpOAuthCoordinator(250行) = 851行 | 单体 McpManager(~974行) | 行数接近，拆分是纯结构优化，不带来功能提升 |

**确定方案**：

1. **❌ 不引入整体架构拆分** — 原因：
   - 本地单体 McpManager 含 Dormant 模式 + 网络感知 + 前台恢复，功能强于上游拆分后版本
   - 拆分为 3 个类是纯结构优化，不带来任何功能提升
   - 引入拆分会丢失 Dormant/NetworkMonitor/ProcessLifecycle 三条恢复链

2. **✅ 引入 `McpStatus.Error.detail` 字段和 `Error.from()` 工厂方法** — 原因：
   - 纯增量改动，不破坏现有逻辑
   - `detail: String? = null` 有默认值，向后兼容
   - `Error.from(throwable)` 自动提取 message + stackTraceToString，改善错误诊断
   - 适配方式：在本地 `McpStatus.kt` 的 `Error` data class 中新增 `detail` 字段 + companion object

3. **✅ 引入 `SettingMcpPage.kt` 错误详情展开展示** — 原因：
   - 上游新增 `errorDetail` 状态 + `AlertDialog` 展示完整堆栈 + 复制按钮

   - 适配方式：在本地 `SettingMcpPage.kt` 的 `McpServerItem` 中添加相同逻辑

4. **✅ 引入 `McpConnectionKey` + `hasSameConnectionParameters()` + `McpConnectionKeyTest`** — 原因：
   - `connectionKey()` 精确区分连接参数（transport/url/headers/oauth token）与工具开关变化
   - 避免用户仅切换工具开关时触发不必要的重连
   - `McpConnectionKeyTest` 3 个测试覆盖：工具元数据不影响 key、url/transport/headers 影响 key、oauth token 影响 key
   - 适配方式：新建 `McpConnectionKey.kt`，在 McpManager 中新增 `connectedConfigs` 追踪 Map 记录每个连接建立时使用的配置；init 链 1 和 `syncAll()` 中用 `hasSameConnectionParameters()` 检测已有 server 的连接参数变化（URL/transport/headers/oauth token），变化时触发 `addClient` 重连、未变化时跳过（工具开关/Schema 变化由下次 `syncAll` 的 `syncTools` 自然刷新）；Error 设置改用 `Error.from()`
