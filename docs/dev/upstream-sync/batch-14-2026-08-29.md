## 详细实施设计

以下 10 项是实施契约，不是 cherry-pick 清单。若实施时发现必须改变 owner、持久化结构或协议范围，应先修订本文，再编码；禁止增加 facade、双读、fallback 或过渡命名。

### 实施项 1：模型选择 sheet 的稳定组合位置（`fa0305ba`）

**现有缺陷**：`ChatPage` 已创建唯一 `ModelListState`，但 `ChatInput` 把 `ModelSelector` 放在 `actionRow` 中；IME 目标变为可见时 `AnimatedVisibility` 移除 action row，`ModelSelector` 内部的 `ModelListSheet` 同时离开组合，搜索框刚获得 IME 就关闭。

**设计**：

- 把 `ModelSelector` 拆成无状态的 `ModelSelectorButton` 与显式 `ModelListSheet`；
- `ChatPage` 继续持有唯一 `ModelListState`，`ChatInput` 只接收并更新同一对象；
- action row 只组合按钮；sheet 在 `ChatInput` 的稳定根级或 `ChatPageContent` 同级组合一次，不受 IME/compact action row 的显示分支控制；
- 选择、清空、dismiss 都只修改同一 state，不保留旧 `ModelSelector` 内部 sheet 或兼容 overload；
- 保留现有 ASR、附件、紧凑高度、折叠屏与 `AdaptiveModal` 行为。

**验证**：Compose/instrumentation 覆盖打开模型列表、聚焦搜索、IME 显隐、旋转、compact height、选择/dismiss 后状态；静态测试锁定同一页面只组合一个 `ModelListSheet`。

### 实施项 2：Qwen 3.8 capability 唯一规则（`0826a3b9`）

**现有缺陷**：本地只有更具体的 `QWEN_3_8_MAX`，且声明 text-only；新增上游通用规则后，最高 match score 仍会让 MAX 命中错误规则。阿里云当前文档明确列出 `qwen3.8-max` 与 `qwen3.8-flash` 原生视觉能力。

**设计**：

- 用一个 `QWEN_3_8` family 定义 `tokens("qwen", "3", "8")`、`visionInput()`、`toolReasoningAbility()`；
- 物理删除语义已错误且被覆盖的 `QWEN_3_8_MAX`，不保留 alias/fallback；
- 不把 `qwen3-max-2026-*` 等不含 `3.8` 的旧 family 误标为视觉；
- 能力仍只由 `Model.inputModalities` 和 `abilities` 派生，不能在附件投影或 endpoint host 再加一套例外。

**验证**：`ModelRegistryTest` 覆盖 `qwen3.8-max`、`qwen3.8-flash`、常见分隔符/大小写、`qwen3-max-2026-*` 不受影响、相邻 Qwen family 不串匹配，并验证附件 readiness 最终读取同一 capability。协议依据：[阿里云 Qwen 视觉能力清单](https://help.aliyun.com/en/model-studio/add-vision-skill)。

### 实施项 3：终端关闭确认（`bce78766`）

**设计**：

- `WorkspaceTerminalPage` 只保存 `pendingCloseTabId: String?` 这一 UI 临时状态；点击关闭先设置待确认 ID；
- 对话框展示 query port 当前 tab 的标题；确认后调用既有 `WorkspaceTerminalVM.close(tabId)`，最终仍由 `WorkspaceApplicationService` → `WorkspaceTerminalRuntime` 串行关闭；
- tab 在确认期间因 shell exit/Workspace 删除而消失时，自动清除 pending，不再发送无意义命令；
- rename、reorder、select、viewport binding 不受影响；不把确认状态写入 Runtime 或 Room；
- 正常用户可见文案同步 `values`、`values-zh`、`values-ja`、`values-ko-rKR`、`values-ru`。

**验证**：UI 测试覆盖取消、确认、目标消失、多个 tab、创建中 tab 与重复点击；Workspace runtime 的现有关闭/创建竞态测试继续作为 owner 证据。

### 实施项 4：request-only 消息来源跟踪（`942d0d28`）

**现有缺陷**：`GenerationLoop` 先创建 System，再依次运行 Time、PromptInjection、Placeholder、Document、Template、Workspace 等 transformer。当前 `TemplateTransformer` 会处理 System、时间提醒、模式注入和 Workspace 提醒，导致内部上下文被用户 message template 二次包裹。

**拒绝上游实现的原因**：`UIMessage` 是 durable/Provider/UI 共用模型。新增 `@Transient isSynthetic` 会把请求构建事实塞进持久模型；copy、反序列化和 Provider replay 还会让真假来源依赖偶然对象路径。

**设计**：

- 在一次 `List<UIMessage>.transforms()` 调用内部创建 `RequestMessageOriginTracker`，只保存该请求的 synthetic message ID 集合；它是 `TransformerContext` 的 request-scoped capability，不序列化、不跨请求缓存；
- `GenerationLoop` 把本次新建的 System ID 注册为 synthetic；
- `TimeReminderTransformer` 注册新建提醒；`PromptInjectionTransformer` 注册新建消息以及被注入内容改写的既有 System；`WorkspaceReminderTransformer` 注册其改写的 System；
- `TemplateTransformer` 只跳过 tracker 标记的消息。`PlaceholderTransformer`、Document 展开和后续 `AttachmentProjectionTransformer` 顺序不变；
- tracker 只表达本次 request origin，不成为 capability、durable fact 或 UI 状态源；
- 删除任何临时 `UIMessage.isSynthetic` 方案，不保留兼容字段。

**验证**：纯函数/管线测试分别覆盖 System、时间提醒、BEFORE/AFTER/TOP/BOTTOM/AT_DEPTH 注入、Workspace 提醒不被 template 包裹；普通 durable USER/ASSISTANT 文本仍应用 template；copy 后 ID 语义稳定；Master/Target 使用同一 pipeline 规则；序列化 fixture 证明 `UIMessage` schema 完全不变。

### 实施项 5：后台生成 Android lifetime adapter（`c62f1eb1`）

**目标**：用户从可见页面发起 Master 生成后，即使 Activity 进入后台，Android 仍把网络流视为用户可见的持续工作。

**唯一 owner 设计**：

```text
用户发起/继续 Master turn
  -> ConversationRuntime 安装 ActiveTurnRuntime（唯一运行事实）
  -> GenerationForegroundLifetime.ensureStarted(conversationId)（单向平台请求，无状态）
  -> ChatGenerationForegroundService
       collect ConversationQueryService.conversationActivities()
       只要存在 RESPONSE_GENERATION 就保持 foreground
       全部结束/进入 AWAITING_APPROVAL 即 stopSelf
       timeout -> ConversationApplicationService.stopGeneration(ids) -> stopSelf
```

- service 不保存 generation ID、turn map、Job、消息或 durable 状态，不提供 acquire/release 计数；
- `ConversationRuntime`/`TurnEngine` 仍是生成、取消、终态和恢复的唯一 owner；service 只是 Android 生命周期消费者；
- `APPROVAL_REQUIRED` 不算持续生成，避免用户长时间不审批占用 FGS；Target 运行由其 Master 的 RESPONSE_GENERATION 自然覆盖，不建第二套 Target service；
- 可见聊天页的屏幕唤醒由 `ChatPageContent` 独占，并直接绑定 `ConversationPresentation.isActive`；因此审批等待期间页面仍可保持亮屏，但这不构成后台持续生成；
- FGS 不调用 `KeepScreenOn`、不操作 Window flag，也不读取 UI 的 `isActive` 作为保活条件。亮屏与后台存活分别由 UI presentation 和 `conversationActivities()` 投影驱动，按各自平台策略消费同一 Runtime 事实，不互相充当状态源；
- FGS 启动失败只记录 typed platform diagnostic，不能取消或伪装 turn 失败；正常生成仍按现有终态收口；
- `ChatNotificationManager` 继续负责流式/完成通知内容。FGS 使用独立稳定 notification ID，仅展示保活状态和回到当前会话的 intent；不能用通知事件反推生成是否活跃；
- Manifest 增加 `FOREGROUND_SERVICE_DATA_SYNC` 与非导出 service；只允许在用户可见操作安装 active request 后启动；
- Android 15+ `dataSync` 共享 6 小时/24 小时限制，`onTimeout(startId, fgsType)` 必须先在数秒内 `stopSelf(startId)`，再由 AppScope 经 application command 请求停止所有 projected active Master turn；不能让平台收口等待投影、网络取消或普通 finally；
- 上线前核对 Play Console FGS declaration 与 `dataSync` 用途；若政策不接受该类型，不得换成无依据的 `specialUse` 绕过。

**验证**：JVM 测 query activity → service decision reducer，并由静态契约锁定 `ChatPageContent` 是 `KeepScreenOn` 的唯一页面调用方；instrumentation/真机覆盖前台转后台、多个并发会话、审批停驻时可见页面仍亮屏但 FGS 已停止、页面退出或 turn 进入 `IDLE` 后释放 Window flag、用户 stop、通知权限开关、FGS 启动拒绝、系统 timeout、进程杀死后的 `TurnRecovery`。Android 的 FGS 启动限制与 timeout 依据：[Android services](https://developer.android.com/develop/background-work/services)、[FGS timeout](https://developer.android.com/develop/background-work/services/fgs/timeout)。

### 实施项 6：非交互 shell EOF 与环境（`b62d29d1`）

**设计**：

- `Process.readResult()` 在 `stdin == null` 时也立即关闭 `outputStream`，明确告诉子进程没有输入；有 bytes 时仍由唯一 `StreamWriter` 写入、flush 并 close；
- `HostShellRunner` 与 `ProotShellRunner` 共用该 EOF 语义；interactive terminal 不调用 `readResult`，不受影响；
- 仅在 `ProotLaunchSpec.from(command != null)` 的 guest `/usr/bin/env -i` 参数中加入 `CI=1`、`NO_COLOR=1`、`PAGER=cat`，交互式 `command == null` terminal 保持原环境；
- timeout/线程中断仍强杀进程、回收 collector/writer；不得吞取消或让 EOF writer 泄漏；
- 不修改 PRoot loader/exec、mount、cwd、kernel release 或持久化。

**验证**：workspace 单测以真实子进程覆盖 null stdin 立即 EOF、非空 stdin 完整 round-trip、空 byte array、timeout、interrupt/cancel、stdout/stderr 截断；`ProotLaunchSpecTest` 区分非交互与 interactive env。

### 实施项 9：MCP OAuth loopback（`b6df5f04`）

**目标与当前问题**：当前 `measix://mcp-oauth-callback` 依赖自定义 scheme。MCP 2025-03 授权规范要求 redirect 为 localhost 或 HTTPS；loopback 可提升与严格授权服务器的互操作性。但上游新建通用 `oauth` 模块、独立 HTTP client 和 service-side session map，会重复本地已有 `McpOAuthCoordinator`/`McpOAuthClient` 责任。

**设计**：

- `McpOAuthCoordinator` 继续拥有 discovery → DCR/手工 client → PKCE/state → browser → code exchange → CAS persist 的唯一工作流；
- 在现有 MCP 包内增加窄接口 `McpOAuthCallbackServer`，只拥有 loopback socket 与一次性 callback session，不抽成无第二 consumer 的通用 oauth 模块；
- 每次授权绑定 OS 分配的 ephemeral port（port 0），优先尝试 `127.0.0.1` 与 `[::1]` 并使用实际成功地址；只绑定 loopback，不能监听 `0.0.0.0`；
- redirect path 固定为 `/callback`，用高熵 `state` 绑定 coordinator lease；request line、headers 与 query 均有硬上限，未知 path/state、畸形或超限请求不能消费有效回调；只接受一次合法 code/error；页面响应 `Cache-Control: no-store`，日志不输出 code/token/verifier；
- PKCE、`resource`、canonical server URI、authorization/token endpoint HTTPS 与当前 trust boundary/revision CAS 全部保留；callback 到达后及 token 持久化前再次验证 server URL、headers、transport 和 OAuth revision，旧回调不能写入新 definition；
- DCR 注册 native public client，并保存现有 client ID/secret；redirect 完整 path 固定、端口可变，依 RFC 8252 的 loopback 端口例外复用 client；若某授权服务器错误要求固定端口，只返回明确互操作错误，不回退自定义 scheme；
- discovery resource、authorization server issuer、authorization/token/registration endpoint 均执行 HTTPS 与精确匹配校验；Android foreground callback service 只为浏览器授权期间保活 loopback socket，引用计数 lease 保证并发授权不会相互停止，使用已有 `FOREGROUND_SERVICE_SPECIAL_USE` 时必须声明精确 subtype/商店用途；它不保存 token、MCP config 或授权阶段；
- 同一交付物理删除 `McpOAuthCallbackActivity`、Manifest deep link、`AppEvent.McpOAuthCallback` 和旧常量，不保留双回调/fallback；
- 保留 refresh single-flight 与 `McpRuntimeCoordinator` 的 server runtime owner，不把 token refresh 移到 callback service。

**验证**：单元测试覆盖 IPv4/IPv6/port collision、并发不同 state、重复/未知 state、超长 query、error response、timeout、用户取消、server config/revision 在浏览器期间变化、token exchange 失败、refresh race；instrumentation/真实 MCP Server 覆盖浏览器后台、进程压力、FGS 被拒绝和返回 App。规范依据：[MCP 2025-03 Authorization](https://modelcontextprotocol.io/specification/2025-03-26/basic/authorization)、[MCP 2025-06 Resource Indicators](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)、[RFC 8252 Native Apps](https://www.rfc-editor.org/info/rfc8252/)。

### 实施项 10：按时间范围清理托管文件（`7da69770`）

**拒绝上游实现的原因**：上游 `FilesManager.deleteOlderThan()` 直接枚举目录、先删 payload 再删 row；本地上传文件还拥有 Artifact metadata、message/settings 引用、CREATING/ACTIVE/DELETING 状态和 cleanup recovery，照搬会形成第二删除 owner。当前设置页还直接依赖 `GeneratedMediaStore`，本项触及该页面时必须一并收口 UI port，不能新增临时 facade。

**设计**：

- 新建真正的 `FileManagementApplicationService` 与 `FileManagementQueryService`，为设置页提供 typed category/range command 与 `ManagedFileUiModel`；页面/VM 不再直连 `GeneratedMediaStore`，上传仍由 `ArtifactUseCase`/`ArtifactStore` 执行；
- command 形状为 `cleanup(category, range)`，range 只允许 `OlderThanDays(7|14|30)` 或 `All`；application service 用注入 Clock 一次计算 cutoff，避免长任务里时间漂移；
- `ArtifactUseCase.deleteUploadsCreatedBefore(cutoff)` 调用 `ArtifactStore.deleteUserRequestedFolderCreatedBefore()`。Store 在同一 lifecycle lock 下快照符合 folder/state/createdAt 的候选，先检查 pins，再逐项复用 `deleteUserRequestedLocked`、`finishUserDeletion` 或 `discardCreating`；引用解除、Settings root、CAS、payload tombstone 与 cleanup pending 语义完全复用现有协议；
- `GeneratedMediaStore.deleteCreatedBefore(cutoff)` 在自己的 persist lock 下查询 `GenMediaEntity.createAt`，逐项复用 `deleteEntityLocked`；它仍是生成媒体 row/payload 的唯一 owner；
- 两个 owner 各自返回领域结果（Artifact 包含 `skippedInProgress`，GeneratedMedia 不伪造该状态），application service 映射为统一 `FileCleanupResult(deleted, cleanupPending, skippedInProgress, failed)`；UI 不把部分成功压成 Boolean；取消在项目边界传播，已取得单项删除所有权后的终态清理由既有协议收口，未处理候选保持原状；
- `All` 也经同一个 application command 调现有 bulk owner，不保留旧页面直调路径；
- cutoff 查询只使用现有 `artifact.created_at` 和 `genmediaentity.create_at`，不新增表/列；上传历史引用删除后的显示与 `attachment_not_found` 规则保持一致；
- 五个 locale 同步范围、确认、部分结果和失败文案；确认中展示 category、范围和当前 query 候选数，不把全列表数冒充实际删除数。

**验证**：Artifact 测试覆盖 message/settings 引用、CREATING/DELETING 恢复、pin、CAS conflict、cleanup pending、取消与部分进度；GeneratedMedia 测试覆盖 row/payload tombstone、孤儿文件、cutoff 边界；application/query 测试覆盖 category/range、Clock、All 复用和 UI 不直连 owner；真实设备验证大量文件、进程重启后 reconcile 和存储不足。

## 持久化、权限与兼容性结论

| 领域 | 第十四批设计结论 | 实施约束 |
|---|---|---|
| Room | 不新增 schema；文件范围查询复用现有 `created_at/create_at` | 无 migration 9；如实现中需要新列必须先修订本文并补 migration/schema/data-preservation tests |
| DataStore/backup | 不新增 Settings 字段；synthetic origin、FGS、OAuth callback session 都是进程内事实 | `UIMessage` serialization、Settings JSON、MCP config 和 backup manifest 保持兼容 |

| Android 权限 | generation FGS 需要 `FOREGROUND_SERVICE_DATA_SYNC`；OAuth callback 可能使用既有 special-use permission | 必须核对启动时机、timeout、notification 与 Play declaration，设备验收前不能称完成 |
