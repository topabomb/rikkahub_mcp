## 二、两次协议重构对照

### 2.1 上游 `4b9ff1a9` 的设计意图

该提交是 squash 合并，子主题包括：

1. **用 Provider 无关的生命周期事件替换 choices 形 `MessageChunk`**
   - `StreamChunk`：`Text/Reasoning/ToolCall/ServerTool/Image` 的 Start/Delta/End，另有
     `ImageSnapshot`、`Annotations`、`Usage`、`Finish`
   - Provider 只负责把线协议译成这些事件
2. **把分片合并从 Provider / 调用方抽到 `StreamChunkHandler`**
   - 用事件 id 定位 Text/Reasoning/Image part
   - 工具用 `toolCallId` 定位并行调用
   - 非流式走 `handleTextGenerationResult` + `TextGenerationResult`
3. **传输无关解码**
   - `SseEvent` + `StreamChunkDecoder.accept/onClosed`
   - Claude / Google / Chat Completions / Responses 各一个 Decoder
   - 为以后从 OkHttp 迁到 Ktor 做准备
4. **用真实 SSE 轨迹做回归**
   - `trace-cli`（Bun + YAML）录制
   - `ai/src/test/resources/stream-traces/` 回放快照
   - 覆盖 DeepSeek、OpenRouter、Gemini 图像、Responses 服务端工具
5. **顺带修了一批具体协议缺陷**
   - 图片在解析源头产出完整 data URI，合并层不再补 `png` 前缀
   - OpenRouter `reasoning_details` 只回传给 `openrouter.ai`
   - Responses `incomplete` / `failed` 显式失败
   - Claude `pause_turn` 后重映射服务端工具块索引
   - 并发工具调用回传顺序

### 2.2 本地已经有、且不能被覆盖的层

| 本地契约 | 为什么不能被 `4b9ff1a9` 整包替换 |
|----------|----------------------------------|
| `OpenAIEndpointProfile` / `ResponseEndpointProfile` | host → vendor / wire / source 的唯一入口；未知网关保持 `COMPATIBLE`，不用 modelId 猜方言 |
| Part / Message 级不透明 metadata | Claude signature / redacted、Gemini thoughtSignature、Responses 整批 output、sourceProfile 隔离 |
| `handleMessageChunk` 的 step 边界 | 已执行 Tool 是步骤边界；当前步骤强制 Reasoning → Text → pending Tools，满足 DeepSeek 回放 |
| `messageId + toolOrdinal` locator | 审批、结果合并、子助手 lineage 不依赖可能为空或重复的 Provider `toolCallId` |
| Generation `Phase` / `Checkpoint` / `Finished` | 子助手恢复、交互上限、非交互审批依赖这些应用层事件，不是 SSE 事件 |
| MCP 完整 `JsonObject` Schema | `$defs/$ref/$schema` 必须保留；不能退回封闭 `InputSchema` |
| 子助手运行时 | Target 工具交集、recovery gate、Child lineage、ask_user 桥接 |

### 2.3 上游方案的价值（要吸收的经验）

1. **流事件应是协议无关的生命周期，而不是 OpenAI `choices[]` 外壳。**
   本地 `MessageChunk` 仍是 Chat Completions 形状。GenerationHandler、连接测试、TTS
   都在读 `choices.first()`。这是真实的耦合，也是后续维护成本。
2. **解码应与 HTTP 客户端分开。**
   本地四个 Provider 各自在 `callbackFlow` 里解析 SSE。轨迹测试只能打到整条
   OkHttp 路径。Decoder 接口让“一段真实 SSE → 一组语义事件”可以离线回放。
3. **图片必须在解析源头就是可渲染 URL。**
   本批已按此落地：Chat Completions 保留完整 data URI，Gemini 用真实 mime 组装
   `data:<mime>;base64,<payload>`，合并层不再二次加 png 前缀。
4. **完整图像快照和增量 base64 不是一回事。**
   `ImageSnapshot` 替换同一 id，`ImageDelta` 追加。本批只禁止拼接两张完整 URL；
   没有 response-local `eventKey` 前，不能把后一张完整图当成前一张的替换。
5. **内置搜索应按 Provider 能力开门，而不是用 modelId 猜。**
   `gpt-` 子串会让大量 OpenAI 兼容代理误显示 Gemini/OpenAI 内置搜索。
6. **真实轨迹是协议回归的正确粒度。**
   本地目前以手写 JSON fixture 为主，覆盖面够用但不等于供应商真实分片。

### 2.4 上游方案里不能整包接收的部分

1. **`StreamChunkHandler` 用 `toolCallId` 当唯一坐标。**
   本地已经证明 Provider id 可能为空或重复，并为此引入 ordinal locator。
   若合并层退回 id-only，子助手、审批和并行工具会回退到 0.0.15 之前的缺陷。
2. **`StreamChunkHandler` 没有“已执行 Tool 步骤边界”。**
   它按事件 id 更新任意 part。本地为 DeepSeek / Claude / Gemini 回放特意把
   Reasoning/Text 插入当前未完成步骤，而不是追加到列表末尾。整包替换会打散步骤原子性。
3. **`UIMessagePart.ServerTool` 扩大持久化协议面。**
   本 Fork 在早期精简中没有服务端工具 part。第十批拆分 `UIMessagePart` 时明确不恢复
   已删除类型。没有产品需求就引入新 `@Serializable` part，会让旧会话反序列化面变宽。
4. **`trace-cli` 是 Bun/TypeScript 工具链。**
   对 Android 产品没有运行时价值，还会给仓库增加第二套包管理。轨迹 *数据* 将来可以要，
   CLI *本体* 本批不引入。
5. **包移动 `providers/{claude,google,openai}`。**
   本地 Claude/Google 仍在 `providers/` 根下，并带有 0.0.15 的 thinking / Schema 适配。
   单纯为对齐目录而搬迁，冲突成本远大于收益。
6. **把 `generateText` 返回值从 `MessageChunk` 改成 `TextGenerationResult`。**
   这是一次全调用方 API 断裂。本地 `GenerationHandler`、连接测试、非流式路径都要改，
   且与子助手事件模型缠在一起。应作为独立迁移，而不是本批附带项。
7. **OpenRouter `reasoning_details` 提升为所有 Provider 的一等 UI 字段。**
   信封本身有价值，但必须保持 host 限定和 source isolation。本批按这个约束落地：
   只解析到 `OpenRouterReasoningMetadata`，且只在 `openrouter.ai` 回传。

### 2.5 结论：分三层吸收，而不是一次换心

| 层 | 本批 | 以后 |
|----|------|------|
| 产品可见 / 低风险 | 模型注册、图标、WebView 释放、内置搜索按 Provider 开门 | — |
| 可独立落地的协议修复 | 图片在解析源头产出完整 data URI；合并层不再补 png 前缀、不拼接两个完整 URL；OpenRouter `reasoning_details` 按 host 隔离回放 | 快照替换语义（`ImageSnapshot`，需要 response-local eventKey） |
| 架构方向 | **只落文档，不换实现** | Decoder + 带 step 边界 / typed terminal / eventKey 的 Reducer；真实 SSE 轨迹覆盖多轮闭环 |

一句话：上游证明了“流事件应该独立于 OpenAI 外壳”；本地证明了“合并必须认识步骤边界和不透明状态”。
下一阶段的正确形状是 **Decoder（上游经验）+ Step-aware merger / locator（本地经验）**，不是二选一。

不 cherry-pick，不照搬上游持久化模型；选择性重建其分层方法。

| 判定 | 内容 |
|------|------|
| 直接采纳设计思想 | Provider 无关的流事件、非流式结果类型、传输无关 Decoder、单响应 Reducer、真实 SSE 轨迹回放 |
| 本批已落地 | 图片完整 data URI、OpenRouter host 限定 `reasoning_details`、内置搜索按 Provider 开门 |
| 条件采纳（以后） | Server Tool、Claude `pause_turn`、ReasoningType；须先补本地状态与终止契约 |
| 保留本地实现 | endpoint profile、完整不透明 metadata、Responses 原始批次、步骤边界、工具 ordinal、显式异常终止、子助手事件 |
| 明确不采纳 | 用 Provider `toolCallId` 作为唯一坐标、把 `Finish(reason)` 当作所有终态、用通用 UI part 取代协议原始状态、整包引入 Bun 工具链、为对齐上游而搬包 |

### 2.6 软件工程评估

上游正确识别了本地同样存在的长期债务：流式输出不应继续伪装成 OpenAI `choices[]`；SSE 传输、协议解码、消息聚合和应用层生成状态应当分层；真实供应商轨迹应能离线回放。

它把职责从“每个 Provider 一边读网络一边拼最终消息”收敛为：

```text
Provider: request + wire decode
Decoder: wire event -> domain event
Handler: domain event -> message snapshot
App: consume snapshot and drive generation lifecycle
```

这降低 Provider 间重复逻辑，为替换 HTTP 客户端、离线复现供应商分片、统一图片与工具生命周期建立了接口边界。文本、思考、图片和工具各自具有生命周期，比“一个 choice 里若干可空字段”更准确。

当前上游实现的结构性问题，本地实施时必须避开：

- **提交边界过大。** squash 同时包含接口重写、目录移动、协议修复、Server Tool、UI、trace 工具和 fixtures，难以 review、bisect 和回滚。本地应按“事件契约 → 单协议 Decoder → Reducer → 调用方 → 可选功能”分开提交。
- **领域层放在 `ui` 包。** `StreamChunk` / Handler 属于 AI domain，不是像素渲染。以后应放在类似 `ai/stream` 的领域包；UI 只消费稳定快照。
- **部分 Decoder 仍经过临时 `UIMessage`。** `wire -> UI model -> stream event -> UI model` 往返让 Decoder 继续依赖 UI 抽象。长期形态应直接 `wire -> domain event`。
- **Reducer 身份坐标不够强。** 上游把 `toolCallId` 同时当事件 id、聚合坐标和持久化 wire id。内部事件必须有 response-local 的 `eventKey`；进入应用层后仍用 `messageId + toolOrdinal`。
- **终止语义退化为字符串。** `Finish(reason)` 分不清完成、不完整、失败和提前断流。Responses `onClosed()` / `incomplete` 变成 Finish，比本地“未见终端事件即报错”更弱。
- **Usage 未区分增量与快照。** 一律相加会重复计数。
- **高频不可变复制与无界缓冲。** 缺少背压与发布节奏证据。Reducer 内部应用 mutable buffer，按受控节奏发布快照。
- **轨迹只证明单次 decode。** 不能代替请求构造、工具执行、下一轮回放和持久化验证。上游 GitHub checks 也不足以证明整棵聚合树已验证。

### 2.7 协议交叉检验

**OpenAI Responses。** 事件类型更接近 output item，不必再挤进 choices。缺口是无损回放：上游主要从可见 `UIMessagePart` 重建下一轮 input，没有等价保留 `OpenAIResponseMetadata.outputItemGroups`、wire format 和 source profile。未知 item、批次边界和无法映射到 UI 的 opaque item 都会丢。`store=false` 下原始批次 metadata 是协议正确性底座，不是临时兼容层。`incomplete` 不是成功，transport close 也不能自动 Finish。

**DeepSeek。** 上游 trace 停在 client tool call，未覆盖“执行结果 → 下一轮请求 → 继续思考”。除 Ark 外倾向复用 OpenAI 默认字段，没有独立 DeepSeek source profile。不能证明 OpenAI summary / encrypted content 与 DeepSeek `reasoning_text` 可互换。effort 以官方 Thinking Mode 表为准：`xhigh → high`，不发送 `max`。

**Volcengine Ark。** 本地已把 encrypted reasoning、字符串 function output 和 stateless replay 放在同一来源契约。上游 capability 语义不同，本身不能证明谁符合最新 Ark 行为。没有当前双轮证据前不改本地 profile；Decoder 必须把 Ark opaque state 原样交给 message metadata。

**Gemini。** 把 `thoughtSignature` 纳入 metadata 方向正确，但必须覆盖：任意 Part 都可能带签名；函数调用 id 原样返回；带签名 Part 不能因相邻而合并；思考草图 `inlineData` 不能替换成占位 reasoning 文本。

**Claude。** Server tool 与 client tool 必须区分；`redacted_thinking.data` 必须原样回传。`pause_turn` 次数耗尽要有显式终态。先扩展事件 / metadata / terminal 契约，再移植行为。

**OpenRouter。** Fork 已删除预设，但自定义 base URL 仍可能指向 `openrouter.ai`。本批已按 host 限定落地 `reasoning_details`，不新增用户配置，也不把它做成所有 Provider 的 UI 一等字段。

**Server Tool。** 概念上能避免供应商已执行的工具进入本地审批链，但扩大持久化协议面，也不能代替完整 Responses 原始 output。仅凭 `*_call` 后缀识别过宽。等产品确有展示 / 回放需求，并具备默认值、旧记录兼容、未知 item 可往返但不能误执行后再引入。

### 2.8 采纳决策矩阵

| 上游内容 | 决策 | 理由 / 本地约束 |
|----------|------|-----------------|
| Provider-neutral stream lifecycle | 采纳设计 | 去除 OpenAI choices 抽象泄漏 |
| `TextGenerationResult` | 采纳设计，独立迁移 | 非流式结果不应伪装成 chunk |
| transport-neutral Decoder | 优先采纳 | 便于 fixture 回放和 HTTP 客户端替换 |
| per-response Handler/Reducer | 采纳设计，重写 | 保留 step boundary、opaque metadata、typed terminal |
| ImageDelta / ImageSnapshot | 采纳语义 | 本批先修完整 URL；替换语义需要 eventKey |
| trace fixtures | 采纳方法 | 补多轮闭环和治理；不引入 Bun CLI |
| OpenRouter reasoning details | 本批已按 host 限定落地 | 只写入 `OpenRouterReasoningMetadata` |
| `ServerTool` / `pause_turn` / ReasoningType | 条件采纳 | 先补 typed terminal 与持久化兼容 |
| id-only tool merge / `Finish(reason)` | 不采纳 | Provider id 不可靠；终态必须类型化 |
| Responses 从可见 parts 重建 | 不采纳 | 会损失 raw output groups 和未知 items |
| 通用 OpenAI capability 套 DeepSeek / 丢弃 Ark 加密状态 | 不采纳 | host/endpoint 方言必须分别验证 |
| Gemini 草图转占位文本 / Claude redacted 只留展示 | 不采纳 | 丢失 inlineData / opaque data |
| Provider 包搬迁 / Generation lifecycle 塞进 AI stream | 不采纳 | 冲突面大；应用层职责不同 |

### 7.1 上游重构带来的架构级思路

这些不是本批漏项，而是下次动协议层时的设计前提。

1. **四层必须分开，而且层与层不能互相冒充。**
   传输（SSE/HTTP）、协议解码、单响应聚合、应用生成生命周期是四件事。
   本地今天把前三层揉在各 Provider 的 `callbackFlow` 里，第四层已经独立成
   `GenerationHandler` 的 Phase / Checkpoint / Finished。上游的贡献是把前三层也切开。
   将来不能为了“统一事件”把第四层塞回 ai 模块，也不能让 Decoder 继续绕一圈 `UIMessage`
   再变成事件。

2. **领域事件描述生命周期，不描述 OpenAI 信封。**
   文本、思考、工具、图片各自有 start / delta / end；快照和增量是不同操作。
   `choices[0].delta` 是 Chat Completions 的线格式，不是跨协议领域模型。
   只要调用方还在读第一个 choice，Claude / Gemini / Responses 就会继续被强迫扮成 OpenAI。

3. **身份必须分三套，不能共用一个 id。**
   - response-local `eventKey`：单次响应内聚合 Text/Reasoning/Image/并行工具；
   - Provider wire id（`toolCallId` / `item_id` / `content_block.index`）：可空、可重复、只用于回放；
   - 应用层 `messageId + toolOrdinal`：审批、截断、子助手、ask_user 的稳定坐标。
   上游 Handler 把第一、二套收成 `toolCallId`，这是它不能整包接收的根因。

4. **无损回放是架构约束，不是 Adapter 边角。**
   统一事件只解决“流怎么进来”。本地已经证明“下一轮怎么原样出去”才是更硬的债：
   Responses 完整 `outputItemGroups`、sourceProfile、Claude `redacted_thinking.data`、
   Gemini 任意 Part 的 signature / draft `inlineData`、DeepSeek/Ark 分端点形状。
   事件模型必须能携带 message-level metadata patch；不能从可见 UI part 反推协议状态。

5. **终态是状态机，不是字符串。**
   正常完成、配额/策略导致的 incomplete、Provider failed、传输在终端事件前关闭，
   必须能被应用层区分。上游 `Finish(reason)` 加 `onClosed()` 自动完成，会把半截成功
   写进会话。本地“未见必要终端事件即报错”必须保留，并升级成类型化 Terminal。

6. **能力由 Provider / host 决定，不由 modelId 猜测。**
   本批内置搜索已按此收敛。将来任何“这个模型能不能内置搜索 / 服务端工具 /
   某种 reasoning 信封”都应落在已识别的 Provider 类型或 host profile 上，
   不能再写 `contains("gpt-")` 这类启发式。

7. **协议回归的基本单位是可回放的传输轨迹，不是手写 JSON 样例。**
   轨迹要能脱离 OkHttp、脱离 Bun、在 Gradle 里跑；验收目标是
   request 构造 → 解码 → 工具执行 → 第二轮回放，而不是“这段 SSE 能解成当前 golden”。
   没有多轮闭环，事件重构只证明自己能解码自己。

8. **演进必须可回退、按协议切开，禁止第二次 squash。**
   上游把接口、目录、修复、新功能和工具链打进一次提交，Fork 无法 bisect。
   本地顺序必须是：先锁事件/Reducer 契约 → 抽 Decoder 且旧 API 仍可用 →
   Chat Completions → Gemini/Claude → 最后 Responses。
   Responses 对事件契约约束最强，所以最早定义、最晚切生产路径。

9. **持久化面保持窄。**
   瞬态 `StreamEvent` 不进 Room。`UIMessage` 现有形状优先稳定。
   Server Tool 之类的新 part 是产品能力，不是流重构的必选项；要加必须单独做
   默认值、旧记录兼容和“不可误执行”的契约。

10. **发行与更新链路隔离。**
    协议内部重构不改 `UpdateChecker`、不递增版本、不改 changelog，除非形成用户可见功能
    并进入正式发版流程。

一句话记住：上游教我们**把流切开**；本地教我们**切开之后还要能按原协议拼回去**。
以后要建的是带不透明 metadata 和步骤边界的分层，不是再实现一遍上游的 `StreamChunkHandler`。

### 7.2 目标形状与职责

```text
HTTP / SSE transport
  -> protocol decoder
  -> provider-neutral domain events + provider-opaque metadata events
  -> step-aware per-response reducer
  -> stable UIMessage
  -> GenerationHandler / tools / sub-assistant lifecycle
```

事件属于 AI domain，必须同时表达生命周期和不透明状态：

```text
StreamEvent
  PartStarted(eventKey, kind, providerPartId?, metadata?)
  PartDelta(eventKey, payload)
  PartSnapshot(eventKey, payload)
  PartEnded(eventKey, metadata?)
  MessageMetadataPatched(providerMetadata)
  UsageDelta(...) / UsageSnapshot(...)
  Terminal(Completed | Incomplete | Failed | ClosedBeforeTerminal)
```

- `eventKey` 由 decoder 保证，只在单次响应内唯一；`providerPartId` / `toolCallId` 可空。
- `MessageMetadataPatched` 能承载完整 Responses output groups，而不是只挂在某个可见 part 上。
- snapshot 与 delta 是不同操作；terminal 是状态机事件，不是自由字符串。
- 是否保留 partial、是否允许继续、是否落盘，由应用层显式决定。

Reducer 只管理单响应领域状态：校验 start/delta/end 与 terminal 顺序；维护 eventKey → part；
保留“已执行 Tool 是步骤边界”；不合并带不同 opaque metadata 或 signature 的 part；合并
message-level provider metadata；内部高效累积，按受控节奏发布 immutable snapshot；
terminal 后拒绝或显式记录迟到事件。它不负责 HTTP、请求组装、本地工具执行、审批、
子助手 checkpoint 或 UI。

`GenerationHandler` 继续负责生成循环、上下文、Transformer、工具装配和生命周期。
新的 stream event 不取代 Phase / Checkpoint / Finished，只提供更可靠的消息快照与终态。
`StreamEvent` 是瞬态协议，不直接落 Room。`UIMessage` 现有序列化形状优先保持稳定。

协议内部重构不能进入更新与发行链路：不改 `UpdateChecker`、更新端点、下载委托或忽略版本语义；
架构重构本身不构成递增版本和改 changelog 的授权。

### 7.3 实施顺序

每一步都要能与旧实现做语义对照，保持可回退：

1. 先定义不依赖任何 Provider 的事件、typed terminal、usage 语义和 reducer 契约；用纯手写事件锁住
   step boundary、重复 id、opaque metadata 和终止错误。
2. 抽出 transport framing 与 decoder interface，保持现有 Provider API 可用。
3. 先迁移 Chat Completions，验证通用事件和 reducer，但不把它当作其他协议的模板真理。
4. 分别迁移 Gemini、Claude；以签名、redacted state 和 part boundary 为阻断门槛。
5. 最后切换 Responses；先建立完整 raw output group、多轮 tool continuation、unknown item 和
   source isolation fixtures，再替换生产路径。
6. 全部稳定后再移除 choices-shaped adapter；最后评估 Server Tool UI 等可选能力。

Responses 风险最高：最早定义它对事件契约的要求，最晚切换生产实现。

### 7.4 轨迹治理

真实轨迹方法应采纳，Bun/TypeScript CLI 不必进仓库。若建立 fixtures：

- 保存 SSE event/data 边界，不保存密钥、用户私密输入或不必要 header；
- 记录 Provider、endpoint profile、模型、录制日期、是否脱敏和协议目的；
- opaque signature / reasoning 按敏感测试资产管理；
- semantic snapshot 必须显式 review，不能把“更新 golden”当作修复；
- Gradle 测试独立运行，不要求开发机安装 Bun；
- 以 request-build + tool execution + continuation 闭环为主要验收目标，不只覆盖单次 decode。

### 7.5 验证矩阵

通用流状态机：start/delta/end、空 delta、迟到/重复 end；transport 在 terminal 前关闭；
Provider incomplete / failed；空白、迟到、重复 `toolCallId` 仍由 eventKey 分开；
审批与回填继续用 `messageId + toolOrdinal`；usage delta 与 snapshot 不重复计数；
长文本、长 reasoning、慢消费者和图片增量的内存/发布节奏。

Provider 闭环：

- OpenAI Responses：`store=false`、多轮工具、完整 output batches、unknown item、提前断流；
- DeepSeek：Chat 与 Responses 分开，`reasoning_text`、第二轮 continuation、官方 effort 表；
- Ark：encrypted state、字符串 function output、第二轮 continuation、source isolation；
