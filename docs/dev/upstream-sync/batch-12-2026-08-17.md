## 二、逐提交分析

### 2.1 `5b390510` Allow pausing update reminders

**上游改动**：把 `DisplaySetting.showUpdates: Boolean` 替换为 `updateCheckDisabledUntilEpochMillis: Long`。设置页从开关改成 7/14/21 天暂停对话框；`ChatVM` 用 `flatMapLatest` 按时间戳开关检查流；抽屉用 `LaunchedEffect` 到期后重新显示卡片。

**正确性**：暂停到期自动恢复比永久关闭更不容易让用户漏掉安全/功能更新。实现本身合理。

**不合理 / 不能整包接收**：

1. **丢掉永久关闭且无迁移。** 旧 `showUpdates=false` 会被忽略，新字段默认 `0`，已关闭提醒的用户会重新收到检查。这是持久化兼容错误。
2. **`ChatVM` 自管更新流与本地架构冲突。** 本地 `UpdateChecker` 是 Koin 单例，`stateInOnce` + `SharingStarted.Lazily`，由 `UpdateCard` 首次组合触发一次进程级检查。上游让每个 `ChatVM` 重新 `flatMapLatest`，会拆掉“全进程只请求一次”的契约。
3. **产品上只允许最长 21 天。** 可接受为新 UI 默认，但不能让旧的永久关闭失效。

**本地落地**：

- 保留 `showUpdates`。
- 新增 `updateCheckDisabledUntilEpochMillis`，默认 `0`。
- `DisplaySetting.areUpdateChecksEnabled(now)` = `showUpdates && now >= pauseUntil`。
- 设置页改成暂停对话框；`showUpdates=false` 显示为已关闭，点“立即恢复”写回 `showUpdates=true` + `pauseUntil=0`。
- 抽屉用该谓词 + 到期 `LaunchedEffect` 控制 `UpdateCard`。
- **不改** `ChatVM` / `UpdateChecker` 的检查流。

**判定**：✅ 同步（按本地更新架构适配）  
**优先级**：P1  
**持久化**：新增 Long 字段，默认 0，旧配置可反序列化；旧 `showUpdates=false` 继续生效。

### 2.9 `f55c8c14` null tool_calls / choices / delta 解码崩溃

**上游**：`StreamChunkDecoder` 把 `jsonArray`/`jsonObject` 改成 `*OrNull`。部分兼容网关把 `tool_calls` / `choices` / `delta` 写成 JSON `null`。

**本地没有 Decoder。** `parseMessage` 已用 `as? JsonArray`，`tool_calls: null` 安全。流式路径仍是：

```kotlin
it["choices"]?.jsonArray
choice["delta"]?.jsonObject
```

`JsonNull` 上的 `jsonArray`/`jsonObject` 会抛，整轮生成中断。

**落地**：抽出 `parseStreamPayload`，对 `choices`/`delta`/`message` 用 `jsonArrayOrNull`/`jsonObjectOrNull`。不引入 `StreamChunk`。

**判定**：✅ 同步（适配到本地流式解析）  
**优先级**：P0

### 2.10 `edbd5773` reasoning 支持 max effort

**上游**：`ReasoningLevel.MAX(32000, "max")`；Chat Completions 把 `MAX` 映射为 `"max"`；选择器增加 Max。web-ui 变更跳过。

**与第 11 批的关系**：当时明确“没有单独 MAX，XHIGH 不发送 `max`”。现在有独立级别，可以诚实映射：XHIGH 仍按文档别名，MAX 才发 `max`。

**不能照搬上游 Chat Completions when**：本地 `OpenAIEndpointProfile` 按 host/model 映射。官方 OpenAI 不接受 `"max"`（只有 none/minimal/low/medium/high/xhigh）。`MAX` 在官方 OpenAI 上必须落到该模型支持的最高档，不能发 `max`。

**本地映射**：

| 端点 | MAX | XHIGH（不变） |
|------|-----|----------------|
| DeepSeek Chat / Responses | `max` | `high` |
| NVIDIA DeepSeek-V4 | `max` | `max`（原有） |
| 官方 OpenAI | 与该模型 XHIGH 相同的最高档 | 按现有表 |
| 未知兼容网关 / OpenRouter / OpenCode | `max`（`level.effort`） | `xhigh` |
| Claude adaptive 无 xhigh | `max` | `max` |
| Claude 手动 thinking + effort | `high`（与 XHIGH 相同封顶） | `high` |
| Gemini 3 | `high` | `high` |

**持久化**：新枚举 `@SerialName("max")`，旧配置无此值，默认不受影响。`fromBudgetTokens` 最近邻会把接近 32000 的预算判为 MAX。

**判定**：✅ 同步（按本地 endpoint profile 映射；跳过 web-ui）  
**优先级**：P1

### 2.11 `0c52b62b` 不要回放加密思考的明文

**上游**：Responses 重建 reasoning item 时，若有 `encrypted_content` 则不放 plaintext `content`。

**正确性**：OpenAI 无状态续轮要的是加密状态，不是可见摘要。两者一起发可能被拒或行为未定义。issue #1719。

**本地**：OpenAI/兼容路径总是放 `summary`（可空）再附 `encrypted_content`。DeepSeek 走 `reasoning_text`，不用加密字段，必须保持。

**落地**：仅在非 `usesReasoningTextContent` 路径：有 `encryptedContent` 时省略 `summary`，只回传 `id` + `encrypted_content`。source profile 隔离不变。

**判定**：✅ 同步（适配到 summary / reasoning_text 分路径）  
**优先级**：P0
