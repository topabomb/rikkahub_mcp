## 详细实施规格与逐项正确性分析

下面 15 项不是 cherry-pick 清单，而是按当前架构冻结的实施契约。每项都明确价值、owner/调用链、必须保持的正确性条件和验收证据。实施时若代码事实迫使 owner、持久化结构或协议范围发生变化，必须先修订本节；不得以兼容 facade、旁路写入或只覆盖 happy path 的方式绕过。`c167c70e` 仅保留在后文调研记录，不属于这 15 个实施项。

### 实施项 1：think 标签开头解析（`85402745`）

**为什么引入**：当前 `ThinkTagTransformer` 的正则未锚定，会把正文示例里的 `<think>` 误当 reasoning；这是实际解析错误。上游修复了方向，但没有本地 `StreamingMessageTransformer` 的 active-message-only 和结束收口契约。

**实现约定**：

- `ThinkTagTransformer` 继续同时处于 Master/Target 共用的 output/streaming pipeline，不新建第二转换器；
- 提取一个只处理当前 active assistant 的纯函数；同一 `UIMessage` 内以最后一个已执行 Tool 为 assistant→tool step 边界，匹配必须等价于 `\A\s*<think>...`，且只检查当前 step 的第一个非空白 `Text` part；
- 当前 step 已有 Provider 原生 `Reasoning` 时，标签 fallback 必须停用，不能同时产生两份 reasoning；已完成 step 的 Reasoning 不得抑制后续 step；
- `transformStreaming` 每个 chunk 只变换当前 active assistant，不遍历或重写历史；`onStreamingFinish` 负责给未闭合 reasoning 补 `finishedAt`；
- 相同累计消息被重复变换必须幂等：不重复插入 `Reasoning`、不改变既有 `createdAt`、不重复剥离正文；
- 保持当前 pipeline 次序，使 think 标签转换先于后续 regex/资源终态处理，不覆盖 `TurnPipelineFactory` 的 Master/Target 共用装配。

**正确性证据**：扩展 transformer 测试覆盖开头标签、前导空白、正文中间 literal、当前 step 后续 `Text` part、当前 step 原生 reasoning、跨已执行 Tool 的多 step、闭合时间只在同一 step 复用、未闭合流式内容、结束收口和重复 chunk；保留 `StreamingTransformScopeTest` 对“历史消息逐 chunk 零次进入”的静态行为锁定，并分别经过 Master/Target pipeline 测试。

### 实施项 2：上下文消息上限数字输入（`adf333ec`）

**为什么引入**：滑块难以精确设置较大的消息数；但上游的最小值 20 与本地 `0` 表示关闭、启用态 `40..512` 的真实契约不同。

**实现约定**：

- UI 使用独立字符串编辑缓冲，输入过程不逐字符写 Settings；只在 IME Done 或失焦时提交；
- 合法提交只能是 `0` 或 `40..512`。空值、非数字、负数和越界值保留在编辑缓冲并显示明确错误，不静默 clamp 后写入；
- 关闭开关写入 `0`；从关闭切回启用写入本地默认值 `80`，不新增持久化的“上次输入”第二状态；
- 提交仍走 `AssistantDetailVM.update` → `ArtifactUseCase.updateSettingsReferences` → `mergeAssistantDelta`/Settings 原子更新链，不能直接写 `SettingsStore`，也不能整份 Assistant 回写覆盖并发修改；
- 外部 Assistant 更新到达时，未编辑状态同步新值；正在编辑的非法草稿不能反向污染 durable 设置。

**正确性证据**：单元测试覆盖解析、边界、开关往返、Done/失焦只提交一次和 `mergeAssistantDelta` 并发字段保全；Compose 测试覆盖错误语义与焦点；五个 locale 都提供正常用户可见文案；生成配置测试证明 `effectiveContextMessageLimit()` 仍是唯一消费语义。

### 实施项 3：DeepSeek V4 Flash Vision Experimental（`f167a855`）

**为什么引入**：该模型确有图像输入能力，而当前更宽的 V4 Flash 规则只声明工具推理，会让附件 readiness 和多模态投影误判为文本模型。

**实现约定**：

- 在 `ModelRegistry` 增加专用定义，按上游真实 model id `deepseek-v4-flash-vision-exp` 同时匹配 DeepSeek、V4、Flash、Vision、Exp token，并声明 `visionInput()` 与 `toolReasoningAbility()`；未发布的 `vision-experimental` 别名不得被测试伪造为已支持；
- 正确性依赖 `resolveModels()` 的最高 `matchScore`，不是列表先后顺序。专用规则必须自然获得高于通用 V4 Flash 的分数；列表只按领域相邻性组织；
- 通用 V4 Flash 继续保持 text-only，不能为了一个具体型号把整个 family 误标为 vision；
- 这项只改变模型 capability/readiness/附件投影，不改变 Provider wire、Conversation 持久化或 Artifact owner。

**正确性证据**：测试精确官方名称、大小写、常见 provider/proxy 前缀、专用规则得分高于通用规则、普通 V4 Flash 仍无 vision，以及该能力能到达现有 `ImageInputAdapter`/附件投影判定。

### 实施项 5：MiMo 完整端点契约（`8b3a1f84`）

**为什么引入**：MiMo 的 thinking 控制有实际互操作价值；但只复制上游 Chat 请求中的 `thinking.type` 会在本地双 API 架构下产生半支持：工具续跑可能丢 reasoning，Responses 还会发送不匹配的 OpenAI 方言。

**实现约定**：

- `OpenAIEndpointVendor` 新增 `MIMO`，识别官方 `api.xiaomimimo.com` 与上游 Token Plan 端点 `token-plan-cn.xiaomimimo.com`；未知兼容 host 不猜测为 MiMo；
- Chat Completions 在 MiMo host 且模型声明 `REASONING` capability 时按本地 reasoning 开关发送 `thinking.type=enabled|disabled`；只有 wire 上实际启用 thinking 时才省略会被忽略的 `temperature`/`top_p`，非 reasoning 模型继续发送 sampling；token 上限使用 MiMo 支持的 `max_completion_tokens`；
- 把 `requiresDeepSeekToolReasoningReplay()` 泛化为端点能力判定。MiMo 工具 continuation 无论用户是否勾选“包含历史思考”，都保留协议要求的历史 `reasoning_content`；普通历史展示偏好不能破坏 wire continuation；
- 因本地允许 `useResponseApi`，必须增加 `ResponseEndpointProfile.MIMO` 和独立 `OpenAIResponseSourceProfile.MIMO`。Responses 的 OFF 映射为 `reasoning.effort=none`，AUTO 省略，LOW/MEDIUM/HIGH 原样，XHIGH/MAX 降为 MiMo 支持的 `high`；
- MiMo Responses 不请求 unsupported reasoning summary/encrypted content，也不复用其他 endpoint 的 opaque item；保留 reasoning text item 供工具 continuation 回放；
- 不引入 `background`、`previous_response_id` 或 `context_management` 等 MiMo 未支持的 stateful 协议；Responses 继续使用已有 `max_output_tokens`；
- endpoint 差异只存在于现有 Chat/Responses builder/profile；不能在 UI、Settings 或 `GenerationHandler` 里散落 host 判断。

**正确性证据**：两种 host × Chat/Responses × stream/non-stream 的请求体测试；覆盖全部 reasoning level、sampling 省略、token 字段、工具 continuation、source profile 隔离和 unrelated compatible host 不变。协议依据：[MiMo Chat Completions](https://mimo.mi.com/docs/zh-CN/api/chat/openai-api) 与 [MiMo Responses](https://mimo.mi.com/docs/zh-CN/api/chat/responses)。

### 实施项 6：备份导入前确认（`f557cef5`）

**为什么引入**：恢复会覆盖完整 durable aggregate 和设置，必须在产生副作用前得到明确确认。上游“立即恢复”的文案和流程不符合本地 staged cold-start 状态机。

**实现约定**：

- 本地文件、WebDAV、S3 的所有恢复入口共享一个确认语义；确认内容明确说明“确认后先校验并暂存，重启后覆盖数据库、托管 payload 与设置，当前进程此刻尚未切换”；
- 选择文件本身可以发生在确认前，但复制到内部临时文件、远端下载和 `stageRestore` 只能在确认后启动；取消/返回不能创建临时文件、staging 或 pending；
- 确认后继续沿现有 UI/VM → sync service → `BackupArchiveService.stageRestore` 链；`BackupArchiveService` 仍是 archive/staging 唯一 owner，`PendingBackupRestore` 仍是 Room 打开前安装与 rollback owner；
- 不允许页面、VM 或 sync client 直接关闭 Room、覆盖 live 文件或恢复 Settings；stage 成功后只展示“需要重启”，不能伪装为当前进程已恢复；
- 恢复中的重复点击要禁用；并发恢复和“已有 pending”返回 typed conflict，不能用第二次覆盖第一个 pending；
- 临时文件在成功、失败、取消后都由其创建 owner 清理；所有 catch 显式重新抛出 `CancellationException`。完整聚合不因确认 UI 而拆分。

**正确性证据**：测试确认前调用次数为零、取消无文件副作用、成功只产生 pending、坏 archive 不污染 pending、并发请求、已有 pending、临时文件清理和重启后安装/失败 rollback；真实恢复需用测试数据验证 DB 与托管 payload 同构，不能只用 JVM mock 代替。

### 实施项 7：终端后台运行与多 Tab（`3a533a6a`）

**为什么引入**：多终端和离开页面后继续运行有产品价值；但上游把 raw session、creation jobs 和 repository 生命周期放进 Page/VM，违反本地 application port 和唯一 owner，并存在关闭与创建交错竞态。

**实现约定**：

- 新建 application-scoped `WorkspaceTerminalRuntime`（最终命名可调整但 owner 只能有一个），独占 session、PTY/process、创建 job、tab 顺序、选中项和 `closeAll`；terminal session 是进程内领域运行态，不并入 `ConversationRuntime`；
- `WorkspaceApplicationService` 暴露 create/select/rename/reorder/close/closeWorkspace 及 rootfs install/reinstall/delete 等 typed command；`WorkspaceTerminalQueryService` 暴露只含 tab id、编号、标题、selected、readiness、finished 的 `WorkspaceTerminalUiModel`；
- UI/VM 不持有 `TerminalSession`、client 或 coroutine `Job`，Android `TerminalView` 通过专用 viewport binding port 按 tab id attach/detach，raw terminal 对象不泄露给页面；
- owner 内所有创建、选择、关闭、shell-exit 和 close-all 通过 actor/单 dispatcher 或同一 mutex 串行化；`creationJobs` 只能在这个串行边界内访问；
- close 先让 tab 从 query state 不可再选，再取消/等待创建并 `finishIfRunning`；创建失败和 shell exit 都走同一 remove/finalize 路径。不能用 `runCatching` 吞 `CancellationException`；
- rootfs install、reinstall、delete 的每个入口都必须先 `await closeWorkspace` 再变更 rootfs，不能只在终端页面按钮补关闭；同一 workspace 的悬空进程必须归零；
- 明确最大 tab/PTY 数和资源超限结果；页面离开/应用进后台保留会话，进程死亡后不持久化虚假的“仍运行”状态；
- 保留本地 PRoot flags、DNS patch、mount、working directory、URL 处理和 extra keys，不用上游 manager 覆盖这些本地语义。

**正确性证据**：owner 状态机测试覆盖 create/close、关闭创建中、并发 create、shell exit、reorder/select、最大数量、close-all 与 rootfs mutation 互斥；Compose 测 tab/viewport attach；Android 14+ 在 `arm64-v8a`、`x86_64` 验证后台、旋转、进程退出、安装/重装/删除。同步更新 `workspace-architecture.md` 和 `application-architecture.md`。

| Room | 不引入上游 schema；fork 只复制现有 header 字段 | 无 Room migration |
| Backup | 不拆分 DB 与受管 payload；导入确认沿用完整聚合 | 不改变 archive/manifest schema |
| Settings | 不引入 `NetworkSetting`；context limit 沿用现有字段 | 不新增 DataStore 字段 |
| Provider wire | MiMo Chat/Responses、OpenRouter session、两种 OpenAI API 的空 tool schema | 外部协议适配，不落盘 |
| Application ports | 新增 terminal owner/query port 与 provider-settings application service；fork 仍走 conversation command writer | 替换 touched UI 直连，不产生第二 writer |
| Skill | 新增安全 YAML 依赖，删除无消费者的 `allowedTools` 内部字段 | skill 文件格式兼容，需许可证清单 |
| Workspace | 多终端 session 仅为进程内运行态 | 不得另造 durable 第二状态源 |

本轮没有发生 Room/DataStore/backup manifest 结构变化，因此不需要 migration。以后若扩展到这些持久化结构，仍必须先补显式 migration、schema 同构和数据保全方案，不能以默认值或兼容 facade 掩盖。
