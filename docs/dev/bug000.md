# `generate_image` 偶发 `artifact_missing` Bug 调研与修复方案

## 一、背景

当前聊天文生图链路中，`generate_image` 成功后会产生一份正式生成媒体和一份供聊天 Tool Result 使用的本地 artifact：

```text
Image Provider
    ↓
生成图片
    ↓
images/...                 ← 正式生成媒体
    ↓
复制
    ↓
upload/...                 ← 聊天 Tool Result artifact
```

当用户同时要求“生成图片并设置为当前助手背景”时，工具还会执行背景替换。

正常完成后 Tool Result 应类似：

```json
{
  "status": "completed",
  "media_id": 76,
  "file": {
    "path": "/upload/xxx.jpg",
    "mime_type": "image/jpeg"
  },
  "background": {
    "requested": true,
    "updated": true
  }
}
```

`ImageGenerationTool` 当前也是按照这个语义实现：图片成功持久化、背景处理完成后，写入 `completed` metadata，并返回 Text + `UIMessagePart.Image(file://...)`。

---

# 二、实际现象

实际出现：

```json
{
  "status": "failed",
  "media_id": 76,
  "file": {
    "mime_type": "image/jpeg"
  },
  "background": {
    "requested": true,
    "updated": true
  },
  "reason": "artifact_missing"
}
```

这个状态本身就是异常组合：

```text
media_id 已存在
+
background.updated = true
+
status = failed
+
artifact_missing
```

说明：

1. 图片 Provider 调用成功；
2. 正式生成媒体已经保存；
3. 背景设置已经成功；
4. `generate_image` 实际已经走过成功路径；
5. 随后供聊天使用的 `upload/...` artifact 被发现不存在；
6. Replay 层又把已经完成的 Tool Result 改写成了 `failed/artifact_missing`。

因此这不是文生图失败，而是**成功之后 artifact 生命周期被破坏**。

同时该问题表现为偶发：相同内容、新建会话、相同外部条件再次执行可能完全正常。这符合典型并发竞态特征，而不符合稳定的 Provider、路径或模型能力错误。

---

# 三、Bug 出现流程

这次场景的重要条件是：

```text
generate_image
set_as_background = true
```

而背景修改属于需要审批的操作。

当前执行流程实际上是：

```text
用户请求生成图片并设置背景
        ↓
LLM 调用 generate_image(set_as_background=true)
        ↓
Tool 进入 Pending Approval
        ↓
本段 Generation Flow 结束
FinishedReason = AWAITING_APPROVAL
```

问题从这里开始。

## 3.1 `AWAITING_APPROVAL` 被错误地当成一次正常生成结束

`GenerationHandler` 已经正确区分：

```text
COMPLETED
AWAITING_APPROVAL
STEP_LIMIT_REACHED
INTERACTION_LIMIT_REACHED
```

但是普通聊天的 `ChatService` collector 对：

```kotlin
GenerationChunk.Finished
```

直接忽略。

随后 `handleMessageComplete()` 的 `onSuccess` 无论真正结束原因是什么，仍然会：

```text
saveConversation(...)
        ↓
generateTitle(...)
        ↓
generateSuggestion(...)
```

当前代码只用 `hasPendingApproval` 阻止“完成音效”，并没有阻止这些正常完成后的后台工作。

因此：

> **等待审批被错误地作为“这一轮已经可以做 completion side effects”的状态处理。**

---

## 3.2 后台任务与审批恢复后的主生成并发运行

随后用户批准背景设置：

```text
用户批准
    ↓
新的 handleMessageComplete()
    ↓
恢复 Pending Tool
    ↓
generate_image 真正执行
```

图片生成成功：

```text
images/xxx.jpg
upload/xxx.jpg
background copy
```

工具将当前内存 Conversation 更新为：

```text
Conversation B

generate_image:
  status = completed
  artifact = upload/xxx.jpg
  Image(file://.../upload/xxx.jpg)
```

与此同时，之前错误启动的：

```text
generateTitle()
generateSuggestion()
```

仍可能在后台运行。

于是形成真正的 race window。

---

## 3.3 后台任务使用旧 Conversation 做整对象写回

`generateTitle()` 在模型返回后会：

```kotlin
val latest = conversationRepo.getConversationById(conversationId)

saveConversation(
    conversationId,
    latest.copy(title = titleToWrite)
)
```

也就是说，它不是：

```text
UPDATE title
```

而是：

```text
读取 DB 中整个 Conversation
修改 title
把整个 Conversation 再写回来
```

`generateSuggestion()` 同样存在这个问题，它获取一个 Conversation，再用：

```text
conversation.copy(chatSuggestions = ...)
```

整对象写回。

如果这个时刻：

```text
内存 Conversation
    已经包含 generate_image completed + artifact

数据库 Conversation
    仍然是较早状态
```

后台任务就可能把旧状态重新覆盖到当前 Session。

于是发生：

```text
Conversation B
有 generate_image Image artifact

        ↓ stale write

Conversation A
没有这个 Image artifact
```

---

# 四、为什么 artifact 会真的被删除

仅仅发生 stale Conversation overwrite，本来还不应该导致文件丢失。

真正让问题升级成数据破坏的是 `ChatService.updateConversation()` 当前的文件清理设计：

```kotlin
private fun updateConversation(...) {
    checkFilesDelete(conversation, session.state.value)
    session.state.value = conversation
}
```

`checkFilesDelete()` 会比较：

```text
oldConversation.files
newConversation.files
```

只要旧 Conversation 有一个 `file://`，新 Conversation 没有，就直接：

```text
filesManager.deleteChatFiles(...)
```

物理删除文件。

因此整个故障链成为：

```text
Tool 成功
    ↓
upload/xxx.jpg 创建
    ↓
Conversation B 引用该文件
    ↓
后台 title/suggestion 拿到旧 Conversation A
    ↓
整对象写回
    ↓
updateConversation(B → A)
    ↓
checkFilesDelete()
发现 B 有文件、A 没文件
    ↓
deleteChatFiles(upload/xxx.jpg)
    ↓
文件真的从磁盘消失
```

下一次模型 step 构建上下文时：

```text
ToolArtifactReplayTransformer
        ↓
materialize(upload/xxx.jpg)
        ↓
文件不存在
        ↓
artifact_missing
```

于是已经完成的：

```text
status = completed
```

又被 `ToolArtifactRewriter` 改写成：

```text
status = failed
reason = artifact_missing
```

---

# 五、根因分析

这不是单点 Bug，而是三个设计错误组合以后形成的严重竞态。

## 5.1 根因一：把 transient Conversation diff 当成文件 GC 条件

这是最严重的设计问题。

Conversation 在生成期间本质上是运行时状态机：

```text
streaming
→ pending tool
→ approved
→ executing
→ completed
→ next model step
→ streaming
```

任何一个状态都可能只是瞬时快照。

当前却采用：

```text
old state 有文件
new state 没文件
        ↓
物理删除文件
```

这个假设不成立。

**状态暂时不再出现 ≠ 文件生命周期已经结束。**

文件删除应该建立在：

```text
明确的持久化删除行为
+
全局确认无引用
```

之上。

而不是建立在：

```text
两个瞬时 Conversation 对象的差异
```

之上。

实际上仓库已经实现了正确的引用语义：`collectFileReferenceTokens()` 不仅检查 `file://`，还把 Tool metadata 中的 `LocalArtifactRef` 定义成正式引用。

但 `ChatService.checkFilesDelete()` 没有遵循这套语义。

---

## 5.2 根因二：后台任务通过 stale snapshot 整对象更新 Conversation

标题生成拥有的字段只有：

```text
title
```

Suggestion 拥有的字段只有：

```text
chatSuggestions
```

但现在它们能够覆盖：

```text
messageNodes
Tool 状态
Tool metadata
artifact 引用
branch 状态
folderId
workspace 状态
...
```

这是典型的 stale-write / lost-update 问题。

原则应该是：

> **异步任务只能修改自己负责的字段，不能把自己持有的旧聚合对象重新提交。**

---

## 5.3 根因三：`AWAITING_APPROVAL` 的生命周期语义错误

`AWAITING_APPROVAL` 不是：

```text
Generation completed
```

而应该是：

```text
Generation suspended
```

当前却：

```text
AWAITING_APPROVAL
    ↓
Flow onSuccess
    ↓
save
title generation
suggestion generation
```

使一个尚未完成的 Turn 与 completion 后台逻辑同时存在。

这极大扩大了 stale-write 的竞态窗口。

---

# 六、非多模态模型的关系

非多模态模型**不是这次 artifact 被物理删除的根因**。

已经存在一条完全不依赖模型多模态能力、能够完整解释：

```text
completed
→ artifact 被删除
→ artifact_missing
```

的代码路径。

但当前非多模态链路确实还有一个值得一起修正的独立问题。

输入 Transformer 当前包含：

```text
AttachmentInputTransformer
...
ToolArtifactReplayTransformer
```

而 `AttachmentInputTransformer` 对非多模态模型负责把：

```text
Image
```

转换成：

```text
OCR observation
或
[Image] placeholder
```

但是 Tool artifact 是随后才由 `ToolArtifactReplayTransformer` 重新 materialize 到 Tool output 中的。

因此：

> Tool Result 中后来 materialize 出来的 Image 并没有完整经过非多模态适配链。

这属于另一个协议/输入投影缺陷。

它可能改变下一 step 的执行时长和时序，因此**可能增加或减少此次 race 被命中的概率**，可以解释为什么之前大量多模态测试没暴露，而这次非多模态模型更容易观察到问题。

但两者需要分开修：

```text
artifact 删除竞态      → Conversation 生命周期问题
非多模态 artifact 输入 → Input projection 问题
```

不能混成一个补丁。

---

# 七、正确的语义设计

修复后应该明确以下四条 invariant。

### 1. Conversation 更新不等于文件删除

```text
updateConversation()
```

只能负责：

```text
更新 Conversation state
```

绝不能隐含：

```text
物理文件 GC
```

---

### 2. 文件删除必须由明确生命周期事件触发

只有这些操作才有资格产生文件清理候选：

```text
deleteMessage
deleteBranch
deleteConversation
明确替换附件
历史压缩后删除旧消息
用户明确删除 managed file
```

然后统一执行：

```text
候选文件
    ↓
全局引用检查
    ↓
无任何持久引用
    ↓
物理删除
```

Tool metadata 中的：

```text
artifact.relativePath
```

同样属于正式引用。

---

### 3. 后台异步任务只能 patch 自己的字段

禁止：

```kotlin
saveConversation(oldConversation.copy(title = ...))
```

改为：

```text
updateTitle(conversationId, title)
updateSuggestions(conversationId, suggestions)
```

同时：

```text
Session 当前状态
    ↓
只 merge 指定字段
```

绝不能用后台任务的旧 snapshot 替换整个 Session。

---

### 4. Tool execution status 与 artifact availability 分离

已经完成：

```text
status = completed
```

就是历史执行事实。

以后即使 artifact 真的由于磁盘损坏等原因不可读取，也不能改成：

```text
status = failed
```

正确语义：

```json
{
  "status": "completed",
  "media_id": 76,
  "file": {
    "available": false,
    "reason": "artifact_missing"
  }
}
```

即：

```text
Execution Status
≠
Artifact Availability
```

---

# 八、明确修复方案

## 8.1 修复 `ChatService` 文件删除职责

修改：

```text
app/.../service/ChatService.kt
```

删除：

```kotlin
updateConversation()
    → checkFilesDelete()
```

也就是说：

```kotlin
private fun updateConversation(...) {
    session.state.value = conversation
}
```

Conversation 普通状态变化不再产生文件系统副作用。

同时删除或废弃当前通用：

```text
checkFilesDelete()
```

---

## 8.2 将文件清理放回真正的生命周期操作

基于仓库已有的：

```text
collectFileReferenceTokens()
ConversationFileReferences
ConversationRepository reference-aware cleanup
```

建立唯一的文件 retention / deletion 路径。

当前 `ConversationFileReferences` 已经定义：

> 候选文件只有在确认不存在任何 `file://` 或 Tool metadata artifact 引用后才允许删除；反序列化失败时宁可保留，也不能误删。

这套语义应该成为所有 Conversation 文件 GC 的唯一标准。

明确迁移：

```text
deleteMessage
delete conversation branch
deleteConversation
compressConversation
明确删除附件
```

到 reference-aware cleanup。

不要再增加第二套 GC 逻辑。

---

## 8.3 修复 title stale write

修改：

```text
ChatService.generateTitle()
ConversationRepository
```

增加窄更新：

```kotlin
updateConversationTitle(
    conversationId,
    title,
)
```

DB：

```sql
UPDATE conversation
SET title = ?
WHERE id = ?
```

Session：

```kotlin
updateConversationState(id) {
    it.copy(title = title)
}
```

禁止再：

```kotlin
saveConversation(latest.copy(title = ...))
```

---

## 8.4 修复 suggestion stale write

同样增加：

```kotlin
updateConversationSuggestions(...)
```

或者如果 suggestions 不独立持久化，则至少：

```kotlin
updateConversationState(id) {
    it.copy(chatSuggestions = suggestions)
}
```

持久化时基于**当前状态**提交，而不是后台任务启动时持有的 Conversation snapshot。

---

## 8.5 正确消费 `GenerationChunk.Finished`

`ChatService.handleMessageComplete()` 必须记录：

```kotlin
FinishedReason
```

最终分支明确：

```text
COMPLETED
    → final save
    → completion sound
    → generateTitle
    → generateSuggestion

AWAITING_APPROVAL
    → save checkpoint
    → 保持 suspended
    → 不启动 completion side effects

STEP_LIMIT_REACHED
    → 对应错误/终止处理

INTERACTION_LIMIT_REACHED
    → 对应终止处理
```

这是生命周期语义修正，不只是为了此次 Bug。

---

## 8.6 修复 Replay 的状态语义

修改：

```text
ToolArtifactRewriter.kt
```

当前：

```text
artifact missing
    ↓
status = failed
reason = artifact_missing
```

改成：

```text
原执行 status 保持不变
```

例如：

```json
{
  "status": "completed",
  "file": {
    "available": false,
    "reason": "artifact_missing"
  }
}
```

Replay 负责的是：

```text
把持久 artifact 投影为当前模型可以消费的内容
```

不是重新判定历史 Tool execution 是否成功。

---

## 8.7 修复非多模态 Tool artifact 输入链

目标语义：

```text
ToolArtifactReplay
        ↓
得到真实 Tool Image
        ↓
统一 Image Input Adaptation
        ↓
NATIVE
或 OCR-derived
或 placeholder
        ↓
Provider request
```

不能：

```text
先完成 Image Adaptation
        ↓
之后又往 Tool output 塞 Image
```

因此需要调整输入投影阶段，使 Tool 内嵌 Image 与普通 Image 共享同一套：

```text
NATIVE / DERIVED / UNAVAILABLE
```

能力判断。

注意：

> 这个转换只作用于“发送给 Provider 的 request view”，不能反写 Conversation 持久状态。

`AttachmentInputTransformer` 自身已经明确声明“Conversation persistence is not modified”，这个原则应继续保持。

---

# 九、TDD 修复执行计划

## Phase 1 — 先锁定竞态

增加集成测试，构造确定时序：

```text
Conversation → Pending generate_image

启动 delayed generateTitle

批准 Tool

generate_image 完成
artifact 创建

让 delayed title 返回旧 snapshot
```

RED 断言：

```text
artifact 不得被删除
Tool metadata 不得消失
Tool output 不得被 stale Conversation 回滚
```

当前代码应稳定失败，从而把这个偶发线上问题转成确定性测试。

---

## Phase 2 — 修正 Conversation update / GC 边界

修改：

```text
ChatService.kt
```

移除：

```text
updateConversation → checkFilesDelete
```

新增测试：

```text
Conversation A 有 artifact
Conversation B 暂时不含 artifact
updateConversation(B)

→ 不能物理删除文件
```

然后为：

```text
deleteMessage
deleteConversation
branch deletion
compression
```

补 reference-aware GC 测试。

---

## Phase 3 — 消除 stale whole-object writes

修改：

```text
generateTitle
generateSuggestion
Repository field-level updates
```

测试：

```text
后台 title 开始

前台 Conversation 新增 Tool Result

title 完成

最终：
title 更新
Tool Result 保留
artifact 保留
messageNodes 保留
```

Suggestion 做相同覆盖测试。

---

## Phase 4 — 修正 Generation lifecycle

增加：

```text
AWAITING_APPROVAL
```

测试：

```text
Finished(AWAITING_APPROVAL)

→ 不 generateTitle
→ 不 generateSuggestion
→ 不触发 completed side effects
```

以及：

```text
Finished(COMPLETED)

→ 正常触发
```

---

## Phase 5 — 修正 artifact status 语义

修改：

```text
ToolArtifactRewriter
ToolArtifactReplayTransformer tests
```

测试：

```text
Tool 历史 status = completed
artifact 文件不存在
```

必须得到：

```text
status = completed
artifact unavailable
```

而不能得到：

```text
status = failed
```

---

## Phase 6 — 补非多模态回归测试

至少覆盖：

```text
generate_image
    ↓
Tool Result Image
    ↓
下一 LLM step
```

分别测试：

```text
Native multimodal model
Non-multimodal + OCR model
Non-multimodal + no OCR model
```

期望：

```text
Native       → Image
Derived      → observation text
Unavailable  → placeholder / unavailable text
```

三种情况下 Conversation 中持久化的原始 Tool artifact 都不能被修改或删除。

---

## Phase 7 — 最终集成验收

必须覆盖原始用户路径：

```text
新建短会话
↓
“生成图片并设置为背景”
↓
Tool approval
↓
图片生成
↓
背景更新
↓
LLM 完成回复
```

并通过压力测试人为改变：

```text
title 返回时间
suggestion 返回时间
Tool generation 时间
approval 时间
OCR 时间
```

重复并发运行，验证 invariant：

```text
1. generate_image 成功后始终 completed
2. background.updated=true 时 artifact 不会因 Conversation 更新被删除
3. title/suggestion 不得覆盖 messageNodes
4. transient Conversation 变化绝不触发物理 GC
5. 只有明确 lifecycle delete + 无引用确认后才删除文件
6. 多模态 / 非多模态只影响 Provider request projection，不影响持久 artifact 生命周期
```

最终修复的核心不是给 `artifact_missing` 加恢复逻辑，而是彻底修正三条错误设计：

```text
Conversation state update ≠ file GC

Async background update ≠ whole Conversation replacement

AWAITING_APPROVAL ≠ generation completed
```

这三条修正以后，此次偶发 `artifact_missing` 的根因才真正被消除。
