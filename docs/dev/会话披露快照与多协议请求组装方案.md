# 会话披露快照与多协议请求组装方案

## 一、结论

本方案把 Memory、可访问子助手以及未来同类“需要告知模型、但不属于用户可见对话”的数据，统一建模为 **Conversation Model Context**。本轮只实现一个聚合的 Disclosure Snapshot，不预建 context-kind registry。

最终方案不是维护一份会被反复覆盖的 Conversation 头部快照，而是：

1. 在每次真正开始新的 `START`（新用户 Turn、编辑后发送或 regenerate）前，从当前有效配置和 Memory 捕获一份完整 candidate；
2. 先按本次结构命令得到目标 selected branch，再与该分支最近一份 Snapshot 内容完全比较；
3. 内容不同时，把新的完整快照作为 append-only model-context entry，由本次 `START` 新建的 Assistant request variant 拥有，并记录其因果 USER anchor；
4. entry 与 Assistant slot、`turn_execution` 在同一个 `StartTurn` Command、同一个 Room transaction 中提交；
5. 请求组装时按 owner Assistant variant 选择 entry，再把它投影为因果 USER Turn 的第一个 model-only text part，后面保持用户原始 parts 的顺序和内容；
6. UI、FTS、消息树渲染和普通会话导出不把 model-context entry 当作用户可见消息。

该结构直接得到正确的时间顺序：

```text
Context Snapshot A
User Turn 1
Assistant / Tool: live state A -> B
Context Snapshot B
User Turn 2
```

后出现的完整 Snapshot 自然覆盖此前基线和此前 Tool mutation，不再需要额外的 `snapshot_generation`、`snapshot_effect` 或“旧代际不得覆盖新代际”的提示词协议。

本轮持久化结论是：

| 持久化域 | 结论 |
| --- | --- |
| Room | 必须从 v9 升到 v10，只增加一张 `conversation_model_context` 表 |
| `ConversationEntity` | 不增加大 JSON 列，保持热 header 行稳定 |
| `message_node` / `UIMessage` JSON | 不塞隐藏消息、不增加 `isSynthetic`、不改变既有序列化结构 |
| `MemoryEntity` | 不改变表结构；查询补 `ORDER BY id ASC` |
| Settings / Preferences DataStore | 不增加 revision、token 或 disclosure 字段，不改变 key 和 JSON |
| 备份 manifest | 继续使用 `rikkahub-durable-v4`，不新增 archive root |
| 工具结果 | 不增加 generation/effect 字段，保留当前领域结果协议 |

唯一新增表是必要的：精确模型上下文必须跨进程、审批、重试、regenerate、Fork 和备份稳定存在，又不能混进可见消息、Settings 或文件 sidecar。除此之外，不为缓存失效判断增加任何持久化结构。

## 二、问题边界

当前有两条动态披露路径：

1. `GenerationLoop` 每个 Provider step 读取 Memory，`buildMemoryPrompt()` 把内容拼入 System；
2. `AssistantToolFactory` 通过 `assistant_manage.systemPrompt` / `assistant_call.systemPrompt` 每 step 从 Settings 重建子助手 Catalog。

此外，`memory_tool.description` 包含当前日期。它们会改变 System 或工具定义，破坏后续消息的可缓存前缀。

需要解决的是：

- 模型在一个 Turn 内必须看到稳定的 Memory 和子助手初始认知；
- Agent 通过工具产生的变化继续由正常 ToolCall / Tool Result 表达；
- 下一次新 `START`（包括 regenerate）能重新取得完整、正确的 live baseline；
- App 重启、审批继续、自动重试和同 Turn 多 step 不重新渲染同一快照；
- 不把模型上下文伪装成用户实际输入或 UI 消息；
- 工具定义、顺序和 Schema 不因日期、Memory 或 Catalog 内容改变；
- 正常历史裁剪后不能长期退回一个已经过期的 durable baseline。

本方案只处理 Memory、子助手披露及其请求组装。它不设计下一阶段的配置下发协议，也不把配置来源写入本轮的数据模型。捕获端只读取应用已经解析好的有效读模型，不依赖 Local Settings 的物理来源。

## 三、先分离三个概念

当前 `UIMessage` 同时承载 durable 消息内容、Provider replay 所需 metadata 和 UI 可见内容。第一版不做全量消息模型迁移，但从架构和 API 上必须明确三种表示不再等价。

### 3.1 Durable Conversation Facts

这是实际保存的会话事实：

```text
Conversation header
selected message tree / variants
Turn / Tool execution facts
ConversationModelContextEntry
→ internal ConversationAggregateSnapshot
```

其中：

- message tree 保存用户、Assistant、Tool 的 canonical durable 内容；
- `ConversationModelContextEntry` 保存模型需要、UI 不显示的上下文；
- 两者同属 Conversation aggregate，由 `ConversationCommandCoordinator` 单写；
- context entry 不是 `MessageNode`：它由一次 durable Assistant request variant 拥有，并另行指向该请求的因果 USER anchor。

### 3.2 Conversation Presentation

这是用户看到的投影：

```text
internal ConversationAggregateSnapshot
+ ActiveTurn streaming projection
+ ToolCallPhase / ConversationPresentation
+ attachment preview / localized renderer state
→ ConversationPresentationSnapshot / ConversationUiModel
```

Presentation 可以重建，不是写协议。含 `modelContextEntries` 的 aggregate snapshot 必须保持 `internal`，只供 command/runtime/request planning 使用；`ConversationQueryService` / `ConversationReadState.Ready` / `ConversationUiModel` 只暴露不含 model context 的 presentation 类型。

现有 `ConversationSnapshot.renderNodes` 的 UI 合并逻辑移入 `ConversationPresentation` projector；aggregate 可以保留 internal `currentMessages()` 等命令读取，但不得作为 UI API 返回。这样不是靠“UI 约定不读某字段”，而是在类型边界上不可见。

### 3.3 Model Request Plan

这是发送给模型的请求级投影：

```text
selected durable messages
+ replay-safe projection
+ context window
+ input transformers
+ model-context entries
+ stable System / tool definitions
→ normalized model turns
→ Provider DTO
```

`ModelRequestPlan` 只存在于一次请求中，不进入 Room、UI 或备份。它可以使用 `UIMessage` 作为现有请求 carrier，但必须携带明确的 durable locator / synthetic origin，不能靠 role、列表位置或对象引用猜测来源。

本轮建立的是边界，不借机把所有 `UIMessage`、Provider DTO 和 Compose UiModel 全量重写成新类型。

## 四、为什么不采用“Conversation 头部单快照 + generation”

原方案把一份当前 Snapshot 放在 Conversation header，并在刷新时覆盖旧内容，再通过 generation 解释后面的旧 Tool Result。该结构有四个根本问题。

### 4.1 它把后发生的状态搬到了历史开头

当工具把 A 改为 B、用户又把状态改为 C 时，把开头 Snapshot 直接改成 C 会形成：

```text
Snapshot C
... historical tool result A -> B
```

generation 只是用额外提示词修补被改乱的时间顺序。append-only context entry 则保持真实顺序，模型不需要学习一套代际覆盖算法。

### 4.2 它无法正确表达历史 Fork

单行只保存“当前 Snapshot”。Fork 到较早消息时，无法恢复该点之前实际存在的 baseline；复制当前值会把未来状态带回历史，清空又会丢掉源分支上下文。

由 Assistant request variant 拥有、指向因果 USER anchor 的 append-only entry 可以随选中历史一起复制，Fork 语义明确。

### 4.3 它迫使配置和 Memory 保存 mutation provenance

为了只在“用户手工修改”时重写头部，原方案需要：

- `MemoryScopeRevisionEntity`；
- `Settings.disclosureManualRevision`；
- `MutationOrigin` 穿过所有 UI、Service 和 Tool 写入路径。

这些字段只服务于缓存失效优化，不是 Memory 或 Settings 的业务事实，而且容易漏掉恢复、导入、默认值演进和未来有效配置源变化。

append-only entry 只出现在新的 `START` 请求位置，不会重写已有前缀。因此每个新 `START` 都可以直接比较完整 candidate；无论变化来自 Agent、用户还是有效配置切换，内容变化才追加，不需要持久化 mutation origin。

### 4.4 它会在历史裁剪后退回过期状态

如果工具修改已经离开 retained window，而单快照仍保持工具调用前的 A，模型会长期回到 A，直到某次手工 revision 触发刷新。这不是普通“遗忘”，而是 durable live state 和模型基线不一致。

新方案在下一次新 `START` 先捕获完整 live state。即使旧 Tool Result 即将被裁掉，新的完整 Snapshot 已经作为尾部 context entry 保存，状态不会退回。

因此删除以下设计：

```text
ConversationDisclosureState.generation
DisclosureSourceRevision
payloadDigest 持久化字段
MemoryScopeRevisionEntity
Settings.disclosureManualRevision
MutationOrigin
Tool Result.snapshot_generation
Tool Result.snapshot_effect
legacy generation 0 解释规则
```

## 五、Durable Model Context 数据模型

### 5.1 Domain model

```kotlin
data class ConversationModelContextEntry(
    val ownerNodeId: Uuid,
    val ownerMessageId: Uuid,
    val anchorNodeId: Uuid,
    val anchorMessageId: Uuid,
    val content: String,
)
```

语义约束：

- `ownerMessageId` 是本次 `START` 创建的 durable Assistant message variant，`ownerNodeId` 是其节点；
- `anchorMessageId` 是该请求实际使用的因果 USER message variant，entry 在 model view 中位于它之前；
- 统一适用谓词同时要求：owner Assistant variant 被选中或仍是 active owner；anchor USER variant 也在同一 selected branch；anchor 是 `planStartTarget` 确认的 owner 因果 USER 且结构位置早于 owner。任一条件不成立都不适用；
- 切换 Assistant 或 USER variant 后，START、请求组装、Fork 和裁剪都必须用同一适用谓词，不能各自猜测；
- regenerate 同一 USER 时创建新的 Assistant owner，不复制、不改写 USER message；
- `content` 是要发送给模型的精确 canonical UTF-8 文本，旧 entry 不在请求时重建；
- JSON envelope 内的 `type` 与 `format` 是唯一内容协议事实；表和 domain 不重复保存 kind / format；
- 第一版每个 owner 最多一份聚合 Snapshot，不增加 registry、plugin 或 section 子表。

### 5.2 Room table

新增一张表，而不是给 `ConversationEntity` 增加大 JSON 列：

```sql
CREATE TABLE IF NOT EXISTS conversation_model_context (
    owner_node_id TEXT NOT NULL,
    owner_message_id TEXT NOT NULL,
    anchor_node_id TEXT NOT NULL,
    anchor_message_id TEXT NOT NULL,
    content TEXT NOT NULL,
    PRIMARY KEY (owner_node_id, owner_message_id),
    FOREIGN KEY (owner_node_id)
        REFERENCES message_node(id) ON DELETE CASCADE,
    FOREIGN KEY (anchor_node_id)
        REFERENCES message_node(id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS index_conversation_model_context_anchor_node_id
    ON conversation_model_context(anchor_node_id);
```

主键是复合 `(owner_node_id, owner_message_id)` 而不是单独的 `owner_message_id`：Fork 与
Child clone 保留 message id、只重建 node id，同一 message id 合法地存在于多个 Conversation；
唯一性与 insert-once 幂等域因此都以 owner node 为作用域。`owner_node_id` 前缀查找与唯一性
由主键 autoindex 承担，只显式声明 `anchor_node_id` 索引。按 Conversation 装载时以
`owner_node_id` JOIN `message_node` 并按 `message_node.conversation_id` 过滤；Conversation
归属只由 owner node 推导，不在 context row 重复保存一个可能冲突的 `conversation_id`。
实体声明和最终导出的 Room schema 必须以 Room 实际生成结果为准。

两个 message ID 位于现有 `message_node.messages` JSON，数据库无法对 JSON 内 variant 建 FK；Repository mapper 因而必须验证 owner/anchor message 确实属于对应 node、角色分别为 ASSISTANT/USER，且两个 node 属于同一 Conversation。Uuid 使用现有字符串格式，不增加第二种编码。

使用独立表的理由：

- `ConversationEntity` 是列表、最近会话、Child、删除和 header 查询的热行，不应携带可能很大的 Memory/Catalog 文本；
- context entry 是随历史追加和删除的事实，不是一个反复覆盖的 header 属性；
- owner/anchor node FK 可以在截断、压缩和删除节点时收口 context 生命周期；variant 删除由同一 Conversation transaction 精确删除；
- Fork 可以按 node/message 映射精确复制；
- 未来增加 Snapshot section 只改变 `content` envelope format，不再改数据库；
- 不需要为每个 section 建表。

表的唯一写 owner 仍是 Conversation aggregate。不得新增可供 UI、Tool 或 Snapshot Service 直接调用的旁路写服务。

### 5.3 为什么必须持久化

只保存在内存中会在以下场景改变模型基线：

- 进程重启；
- 审批等待后继续；
- 同一 Turn 网络重试；
- Provider 多 step；
- Fork / Child clone；
- 数据库备份恢复。

把 content 放入隐藏 `UIMessage` 会污染消息身份、FTS、历史裁剪、UI 和 Provider replay；放入 Settings 则把会话事实交给错误 owner；放入文件 sidecar 无法与 `StartTurn` 原子提交。因此一次 additive Room migration 是必要成本。

## 六、Disclosure Snapshot 内容

### 6.1 Canonical payload

使用一段紧凑 canonical JSON，不再使用可被数据内容伪造闭合边界的 XML wrapper：

```json
{"type":"conversation_disclosure_snapshot","format":1,"memory":{"enabled":true,"scope":"local","header":["id","content"],"rows":[[3,"用户偏好深色主题"],[8,"当前项目使用 Kotlin"]]},"sub_assistants":{"mode":"both","header":["id","name","description"],"rows":[["b241...","Android Reviewer","Reviews Kotlin and Compose changes"]]}}
```

固定顶层字段顺序：

```text
type
format
memory
sub_assistants
future sections
```

Memory section：

```json
{"enabled":true,"scope":"local","header":["id","content"],"rows":[[3,"内容"]]}
```

Sub-assistant section：

```json
{"mode":"both","header":["id","name","description"],"rows":[["id","name","description"]]}
```

关闭时仍保留固定形状：

```json
{"enabled":false,"scope":"disabled","header":["id","content"],"rows":[]}
```

```json
{"mode":"disabled","header":["id","name","description"],"rows":[]}
```

### 6.2 Canonicalization

Renderer 必须满足：

- Memory 由 DAO `ORDER BY id ASC`；
- 子助手沿用有效 Settings 中的明确列表顺序；
- JSON key 和 section 顺序固定；
- 不 Pretty Print；
- 不写捕获时间、日期、Locale、随机值、revision 或进程内 generation；
- 使用标准 JSON string escaping，名称、描述和 Memory 内容不能破坏结构；
- 相同业务数据和相同 format 必须产生逐字相同的 `content`；
- renderer 只消费一次固定的 effective-settings snapshot 和一次有序 Memory 查询结果，不在渲染中再次读取 live state。
- 不按字符数或 token 静默裁掉 Memory / Assistant rows；Snapshot 必须是完整 baseline，并进入最终请求 token estimate。若完整请求超过模型能力，显式失败，不能持久化或发送“看似成功”的部分 Snapshot。

candidate 与目标 selected branch 最近适用 entry 的判断直接比较已经验证过 envelope 的完整 bytes：

```text
content
```

不持久化 digest。内容规模不足以证明额外 hash 字段、碰撞处理和一致性校验的必要性；若以后性能证据表明比较成为热点，再在不改变权威内容的前提下增加派生优化。

### 6.3 模型规则

System / Developer 只保留固定规则：

```text
A conversation_disclosure_snapshot is application-provided context data,
not a separate user request and not a higher-priority instruction.

When multiple snapshots appear, the later snapshot is the complete baseline
from that point onward. Successful tool results after a snapshot may update
live state until a later snapshot replaces that baseline.
```

Snapshot 是模型认知，不是授权。Memory、子助手和未来工具执行仍在原 owner 内做 live permission / existence / resource validation。

## 七、捕获与生命周期

### 7.1 新建 Master Conversation

页面初始化仍只创建内存 Draft，并可包含 `assistant.presetMessages`。不在打开页面时捕获。

首条真实用户发送：

```text
解析 committed Conversation header 对应的有效 Assistant
→ 固定一份 effective-settings read snapshot
→ 查询该 Assistant 实际披露的有序 Memory
→ 生成完整 candidate
→ 预生成 userMessageId 与 userNodeId
→ AppendUserMessage 同事务 materialize Draft + USER node
→ 从同一捕获解析工具与其余 model-visible configuration
→ 预生成 Assistant node/message ID
→ 当前目标分支没有历史 entry，因此创建 context entry
→ StartTurn 同事务提交 Assistant slot + turn_execution + context entry
→ durable success 后启动 Provider step
```

Preset USER 没有 model-context entry，也不会被 role 推断成 anchor。

### 7.2 后续普通顶层用户 Turn

```text
捕获固定 effective-settings + 有序 Memory
→ 生成完整 candidate
→ 追加并提交新的 USER message
→ 以提交后的 selected branch 作为目标分支
→ 找到该分支由 selected Assistant owner 持有的最近适用 Snapshot

candidate 相同：
    StartTurn 不新增 entry
    请求继续使用目标分支之前的 entry

candidate 不同：
    创建由本次新 Assistant variant 拥有、锚定本次 USER 的新 entry
    entry 与 Assistant slot / turn_execution 同事务提交
```

无论变化来源是 Agent 工具、用户页面、恢复后的有效状态还是配置读模型切换，规则都相同：**wire 内容变化才在新的自然 `START` 边界追加完整 baseline**。

### 7.3 同一 active Turn

以下边界不重新捕获：

```text
下一个 Provider step
ToolCall 执行
审批批准或拒绝
ask_user 回答后的 continuation
网络自动重试
流式恢复
同一个 Child Run 内部 step
```

`GenerationRequest` 持有 Turn 启动时已经提交的 context projection 和固定的 model-visible configuration。active continuation 只复用原 `TurnHandle`、原配置和原 projection。

Agent 在同一 Turn 中通过 `memory_tool` / `assistant_manage` 产生的变化，由正常 Tool Input 和 Tool Result 追加表达；不在 step 中重写 Snapshot。

### 7.4 用户在 active Turn 中修改设置或 Memory

不修改正在运行的 request。下一次新的 `START` 重新捕获完整 candidate；若结果相对目标分支变化，追加新 entry。

不需要区分“用户手工修改”和“用户批准 Agent 工具”：它们对当前 Turn 都不重写，对下一次新 `START` 都以实际 live state 为准。

### 7.5 编辑、重新发送、regenerate 与 variant

context entry 以 Assistant request variant 为 owner，以实际 USER variant 为 anchor：

- 编辑 USER 并重新发送时，先提交新的 USER variant / 截断，再以 **完成结构变换后的目标分支** 计算 baseline；
- 纯编辑但不启动模型请求时不创建 entry；
- regenerate Assistant 不复制 USER。它预生成新的 Assistant variant，把即将被替换的旧 Assistant variant 视为 unselected，再计算目标分支 baseline；
- candidate 与该 baseline 不同时，entry 与新 Assistant variant / `StartTurn` 原子提交；相同时只创建新的 Assistant variant；
- 因此，若旧 Assistant variant 正是当前 baseline 的 owner，regenerate 后它会先退出目标分支；必要的相同 live content 会相对于更早 baseline 被判定为变化，并由新 owner 重新落一条 entry，不会丢基线；
- 切换 Assistant variant 后，请求只使用所选 owner 路径适用的 entries；
- 删除 owner 或 anchor message variant 时，Transition 显式删除相关 entries；删除整个 node 时由 FK cascade 收口。

### 7.6 同一 Turn 的 model-visible configuration 必须冻结

只冻结 Snapshot 而继续在每个 Provider step 重读 Settings、模板、Workspace 或时钟，仍会产生语义撕裂：同一 Turn 可能使用旧 Assistant prompt、新工具集合、跨日 placeholder 和另一份 Provider request shape，工具定义也会改写缓存前缀。因此 `START` 必须建立一份进程内不可变 `TurnRequestContext`，作为该 Turn 所有 step 的唯一模型可见配置输入。

概念范围是：

```kotlin
data class TurnRequestContext(
    val assistant: ResolvedAssistantRequest,
    val model: ResolvedModelRequest,
    val mediaCapabilities: RequestMediaCapabilities,
    val promptInputs: FrozenTurnPromptInputs,
    val toolDefinitions: List<FrozenToolDefinition>,
    val toolBindingsByName: Map<String, ToolExecutionBinding>,
)

data class FrozenToolDefinition(
    val name: String,
    val description: String,
    val parameters: JsonObject?,
    val systemPromptContribution: String,
)

data class ToolExecutionBinding(
    val name: String,
    val interactionRequirement: (JsonObject) -> ToolInteractionRequirement,
    val validateArguments: (JsonElement) -> JsonObject?,
    val execute: suspend ToolExecutionContext.(JsonElement) -> List<UIMessagePart>,
)

data class FrozenTurnPromptInputs(
    val messageTemplate: String?,
    val promptInjections: List<ResolvedPromptInjection>,
    val workspaceReminder: String?,
    val turnInstant: Instant,
    val localeTag: String,
    val zoneId: String,
    val conversationSystemPrompt: String?,
    val modeInjectionIds: Set<Uuid>,
)
```

这是责任边界示意，不得把整个 `Settings`、凭据、UI/备份字段塞入对象。`ResolvedAssistantRequest` / `ResolvedModelRequest` 只包含生成 wire 所需的不可变值；传输凭据由 transport owner 提供 live lease。

`FrozenToolDefinition` 是 Provider 唯一可见工具输入：`parameters()` 与 `systemPrompt(...)` 在 `START` 时各求值一次，Schema 做 lossless JsonObject snapshot，prompt contribution 固定为字符串，列表顺序固定。Provider step 不得再访问可执行闭包。`ToolExecutionBinding` 只承担审批前纯参数校验、interaction requirement 和执行；资源存在性、权限与远端状态仍在 execute owner 内 live fail-closed。definition 名称与 binding key 必须一一对应且唯一，否则 `START` 失败。

现有 `Tool` 同时承载动态 wire definition 与执行闭包，必须在本次实现中拆开；不能保留“Provider 优先读 frozen，缺失时回退 `Tool.parameters()` / `systemPrompt()`”的双路径。创建顺序固定为：

```text
读取一次 EffectiveSettingsSnapshot
→ 从该 snapshot 解析 Assistant、Model 和所有影响 wire 的选项
→ 固定 turn clock、Locale、Timezone、模板、prompt injections 与 Workspace disclosure
→ 用同一份 Settings/Assistant 捕获 disclosure candidate
→ 若是新/编辑 USER，先只提交真实用户内容；regenerate 不复制 USER
→ 以结构命令后的目标 selected branch 判定是否需要 context entry
→ 用同一份 Settings/Assistant 捕获 MCP turn capabilities
→ 构造 tools，并物化有序 FrozenToolDefinition + execution bindings
→ StartTurn 原子提交 Assistant slot / turn_execution / 可选 context entry
→ durable success 后以同一 TurnRequestContext 启动 GenerationRequest
```

`AppendUserMessage` 只提交真实 USER；可选 context entry 只随稍后的 `StartTurn` 提交。两者之间若工具准备失败，保留用户消息但不伪造一次已经开始的模型请求。

`GenerationLoop` 的后续 step 可以加入刚提交的 Assistant / ToolCall / Tool Result，但不得通过 `toolProvider`、Transformer 或 Provider adapter 再读 `SettingsStore` 来改变：

```text
System / Developer 内容
Assistant / Model 选择
工具名称、描述、Schema 和顺序
输入转换规则
Provider request shape / media capability
Disclosure Snapshot
```

Transformer 只消费 `FrozenTurnPromptInputs`，不得在 transform 时再读 `SettingsStore`、模板 loader、Workspace 或系统 clock/Locale/Timezone。保存同一个 Transformer 实例不等于冻结；必须冻结它会消费的输入值。

`ConversationRuntime.ActiveTurnRuntime` 持有一个不可变 `TurnRequestContext`。初始 worker 只能以 matching turnId + worker identity 绑定一次；`continueAwaitingApproval` 创建新的 active-worker wrapper 时把同一 context 引用传入，continuation 的 `launchRun` 显式接收它。context 缺失、owner 不匹配或重复绑定都 fail-closed，禁止通过 `effectiveSettings.first()` 重建。进入终态或 supersede 后由 active-request owner 精确释放。

Child 的 context 由对应 SubAssistant Run owner 持有到该 run 终态，同样不得增加独立 registry、按 conversationId 猜测或在 continuation 时重建。

审批 continuation、ask-user continuation 和网络重试复用同一对象。进程重启后当前恢复协议会终结未完成 Turn，因此本轮不新增 `TurnRequestContext` 持久化表或 JSON。

冻结的是模型可见配置，不是权限或外部资源：工具执行前仍由 owner 读取 live permission、目标存在性和资源状态并 fail-closed；密钥等纯传输凭证可以由其 transport owner 刷新，但不得借此改变模型可见请求。Turn 捕获完成后的配置或 Memory 变化从下一次新 `START` 生效。

Settings 和 Memory 不需要跨 owner 的分布式事务。语义切点是已复制的 `EffectiveSettingsSnapshot` 加一次已提交的有序 Memory 查询；从该切点之后发生的修改属于下一次新 `START`。这样既不会持有跨 owner 写锁，也不会把“最新”伪装成无法实现的全局瞬时一致。

## 八、历史裁剪与 Model Request Plan

### 8.1 单一 Planner

继续由 `ConversationContextPlanner` 负责唯一历史窗口和 Tool Result compaction 规划，不增加第二套 Disclosure planner。

`RequestContextPlan` 继续使用现有 `UIMessage` request copy，但必须同时携带不可持久化的来源表，例如：

```kotlin
data class DurableMessageLocator(
    val nodeId: Uuid,
    val messageId: Uuid,
)

sealed interface RequestMessageOrigin {
    data class Durable(val locator: DurableMessageLocator) : RequestMessageOrigin

    data class Synthetic(
        val kind: SyntheticMessageKind,
    ) : RequestMessageOrigin
}

data class RequestContextPlan(
    val messages: List<UIMessage>,
    val originsByMessageId: Map<Uuid, RequestMessageOrigin>,
    // existing trim / Tool Result compaction decisions
)
```

`RequestMessageOriginTracker` 仍是 request-scoped：在进入 transformers 前登记 selected durable message ID → locator，注入型 transformer 登记 Synthetic；普通 `copy()` 保持 message ID，确需更换 ID 的 transformer 必须显式传递 origin。transformers 完成后冻结为 `originsByMessageId`。不把 `isSynthetic` 或 locator 写入 `UIMessage`。

Planner 只通过 durable locator 定位 anchor，不使用“第一条 role=user” fallback。一个 retained anchor 在变换后找不到或出现多个 durable 投影时必须请求失败，不能把 Snapshot 附着到某条 synthetic USER。

### 8.2 裁剪后的 context 选择

先按现有规则得到 selected durable branch 和 retained window，再选择 model context：

1. 通过唯一 `ConversationModelContextApplicability` 过滤：owner Assistant selected/active、anchor USER selected，且 anchor 是 owner 的结构因果 USER；
2. owner selected 但 anchor 已切到另一 variant 时，该 entry 明确不适用，不等待组装阶段以“找不到 anchor”失败；
3. 以 entry 的因果 USER anchor 作为它的逻辑请求位置，而不是 owner Assistant 在 UI 历史中的显示位置；
4. 找到 retained window 第一条真实 selected USER；
5. 在适用 entries 中找到 anchor 位置不晚于它的最近一条 Snapshot，作为 window baseline；
6. baseline 投影到 retained 第一条真实 USER 的 context part 前；
7. retained window 内后续 Snapshot 保持在各自 anchor USER 前；
8. baseline 之前的旧 Snapshot 不发送；
9. 不适用 entry、已删除 node 和窗口外非 baseline entry 不发送。

这不会修改 durable entry 的 owner 或 anchor；“移动到 retained window 起点”只是请求投影。窗口本身已经发生自然变化，因此不会为了 Snapshot 引入额外裁剪规则。

### 8.3 请求组装顺序

```text
1. 从 internal ConversationAggregateSnapshot.nodes 取得 selected durable messages
2. replay-safe projection
3. 运行现有 messageLimit / context window 规划
4. 构建稳定 System 与稳定 Tool definitions
5. 对 durable message projection 运行现有 input transformers
6. 按 durable locator 选择并插入 model-context part
7. 规范化为交替的 model turns
8. 对最终 Provider projection 计算 token estimate 与 ModelStepReceipt
9. Provider adapter 只做 wire DTO 映射
```

Snapshot 在 input transformers 后插入，因此不经过：

```text
messageTemplate
Placeholder
Time Reminder
Workspace Reminder
DocumentAsPrompt
AttachmentProjection
```

用户消息的 transformed request copy 可以变化，但 durable 用户消息和 UI 呈现不被 Snapshot 修改。

### 8.4 Context 与用户 parts 的最终模型 Turn

Provider-neutral 语义是：

```text
USER TURN
  part 0: synthetic disclosure context text
  part 1..n: original transformed user parts
```

这里不是把 JSON 拼进用户文本，也不是修改 durable `UIMessage.parts`。请求层创建一个新的 model projection，context part 和用户 parts 仍有不同 origin；wire adapter 看到的是一个合法 USER turn。

这比强制两条相邻 `role=user` 更正确：Anthropic Messages 会把连续同 role turns 合并为一个 turn；Gemini 官方多轮结构要求 `user` / `model` 交替。跨协议合同不应建立在“相邻 USER 永远保持两个独立语义 turn”的假设上。([Claude API][2])([Google AI for Developers][4])

## 九、多协议编码

所有协议都编码同一个逻辑 USER turn：context block/part 在前，用户原始 parts 在后。禁止伪造 Assistant 消息、协议失败后换结构重试或把 context 提升为 System / Developer。

### 9.1 OpenAI Chat Completions

```json
{
  "role": "user",
  "content": [
    {"type":"text","text":"{...conversation_disclosure_snapshot...}"},
    {"type":"text","text":"Original user request"}
  ]
}
```

图片、文件等原始 parts 继续按现有 content-part 映射跟在 context text 之后。

### 9.2 OpenAI Responses API

```json
{
  "type": "message",
  "role": "user",
  "content": [
    {"type":"input_text","text":"{...conversation_disclosure_snapshot...}"},
    {"type":"input_text","text":"Original user request"}
  ]
}
```

Responses 的 `input` 本来就是有序 input items；本方案只使用一个 user message item 表达一个逻辑用户 Turn，不依赖相邻 USER item 的具体合并行为。([OpenAI API Reference][6])

### 9.3 Anthropic Messages

```json
{
  "role": "user",
  "content": [
    {"type":"text","text":"{...conversation_disclosure_snapshot...}"},
    {"type":"text","text":"Original user request"}
  ]
}
```

Anthropic 明确说明连续 `user` 或连续 `assistant` 输入会被合并成一个 turn，因此应用应主动构造一个明确、有序的 USER content block 列表，而不是把“两个 JSON message”当作模型可见的独立语义。([Claude API][2])

### 9.4 Gemini / Vertex GenerateContent

```json
{
  "role": "user",
  "parts": [
    {"text":"{...conversation_disclosure_snapshot...}"},
    {"text":"Original user request"}
  ]
}
```

Gemini 的 `Content` 表示一个会话 turn，官方多轮示例和说明要求 `user` / `model` 交替；context 因此是 anchor USER `Content` 的第一个 Part。([Google AI for Developers][4])

### 9.5 OpenAI-compatible Endpoint

Grok、DeepSeek、OpenRouter、SiliconFlow、DashScope 等继续走现有 OpenAI provider profile。由于本方案只产生一个正常 USER message，不增加“连续 USER 不兼容”分支，也不需要 endpoint fallback。

### 9.6 Golden contract

所有 adapters 必须验证：

```text
一个逻辑 USER turn
context 是第一个 text block/part
真实用户 parts 是完整、同序的 suffix
没有额外 ASSISTANT
context 没有进入 system/developer
context 没有被模板或附件投影改写
```

## 十、Memory 调整

### 10.1 移除动态 System Memory

删除每 step 的：

```text
GenerationMemoryContext.memories
GenerationRequest.memories
buildMemoryPrompt(memories)
```

Generation pipeline 不再读取 Memory 内容构造 System。`ConversationDisclosureSnapshotService` 只在每次新 `START` 边界读取一次。

Memory Tool 仍需要 owner 和 live write permission，可保留窄上下文：

```kotlin
data class GenerationMemoryToolContext(
    val ownerId: String,
)
```

执行前继续通过原 owner 路径重验 `isStillAllowed`。Snapshot 中存在某 Memory 不代表它仍可写；Snapshot 中没有后来创建的 Memory 也不妨碍按真实 ID 和 live policy 操作。

### 10.2 稳定工具描述

删除 `memory_tool.description` 中的：

```text
Today is ...
```

日期由现有 Time Reminder 上下文负责。工具名称、描述、parameters schema 和列表排序不得依赖日期或 Memory 内容。

### 10.3 不修改 Tool Result 协议

本方案不为 create/edit/delete 结果增加 generation 或 effect，也不为了表面统一顺带重写已有结果格式。Tool Input 已表达修改内容，Tool Result 继续表达成功、ID 或领域失败；Snapshot 的完整重新捕获不依赖解析历史 Tool Result。

### 10.4 有序读取

以下 DAO 查询增加 `ORDER BY id ASC`：

```text
getMemoriesOfAssistantFlow
getMemoriesOfAssistant
getAllMemoriesFlow
getAllMemories
```

这是确定性查询修正，不改变 Room schema。

```text
Target.allowAsSubAssistant
&& Target.id != Caller.id
&& (
```

## 十二、Owner、命令与事务

### 12.1 职责

| 组件 | 唯一职责 |
| --- | --- |
| `ConversationDisclosureSnapshotService` | 从固定 effective-settings snapshot + 有序 Memory 构造 canonical content；不写库 |
| `ConversationApplicationService` / `MasterTurnCoordinator` | 在每个新 `START` 前解析 candidate 和结构变换后的目标分支 baseline |
| `ConversationCommandCoordinator` | `AppendUserMessage` 与 `StartTurn` 的唯一 durable command 入口；只有后者可插入 model-context entry |
| `ConversationTransition` | 纯变换 nodes、selected branch 和 context-entry delta |
| `ConversationRepository` | 在一个 Room transaction 中提交 node、context、execution、artifact/FTS 投影 |
| `ConversationRuntime` | 发布 internal `ConversationAggregateSnapshot`，并随 process-local active request 持有 Master Turn 配置；不成为第二 durable 写 owner |
| `MasterTurnCoordinator` / `DelegationCoordinator` | 从一次 effective snapshot 构造进程内 `TurnRequestContext`，同一 Turn 不重读 model-visible 配置 |
| `ConversationContextPlanner` | 唯一历史窗口、context 选择和 Tool Result compaction planner |
| `GenerationLoop` | 使用冻结的 Model Request Plan 与 `FrozenToolDefinition` 编排 step；按 name 调用 live execution binding |
| Provider adapters | 只映射规范化 model turns 和 frozen tool definitions，不重新求值 context / Schema / tool prompt |
| `ConversationPresentation` / `ConversationQueryService` | 把 internal aggregate 投影成不含 model context 的 UI 类型；禁止向 UI 透传 aggregate |

### 12.2 Snapshot / mutation

内部 aggregate snapshot 增加：

```kotlin
internal data class ConversationAggregateSnapshot(
    val conversationId: Uuid,
    val header: ConversationHeader,
    val nodes: List<MessageNode>,
    val activeTurn: ActiveTurnState?,
    val modelContextEntries: List<ConversationModelContextEntry>,
)
```

它不进入 `ConversationHeader`。`ConversationRuntime` 的事实流改为 internal aggregate；`ConversationPresentation` 从它生成不含 entries 的 UI snapshot，Query Service 不得透传 aggregate。

`ConversationTransition` 提供唯一的纯 `planStartTarget`：基于当前 committed aggregate snapshot、因果 USER locator、regenerate/edit 边界和预生成 Assistant identity，返回 `StartTurn` 将使用的目标 selected prefix、新 owner node/message 和 `expectedSelectedPrefixMessageIds`。不得由 Coordinator 另写一套“排除哪个 variant”的判断。

命令始终携带完整 canonical candidate，而不是携带“调用者已经判定好的 nullable entry”。执行锁内，Transition 重新计算目标 selected prefix：token 不同则 conflict；相同才对当前适用 baseline 做 exact-content comparison，并决定 `insertedModelContextEntries` 是否为空。这样 branch CAS 与判等属于同一个纯 Transition / transaction 计划，不存在 stale `null`。

`AppendUserMessage` 保持只提交真实用户内容。`StartTurn` 扩展 request owner 与因果 anchor：

```kotlin
internal data class StartTurn(
    val turnId: Uuid,
    val assistantNodeId: Uuid,
    val assistantMessageId: Uuid,
    val anchorNodeId: Uuid,
    val anchorMessageId: Uuid,
    val expectedSelectedPrefixMessageIds: List<Uuid>,
    val modelContextCandidate: String,
    val epoch: Long = 0L,
) : ConversationCommand
```

约束：

```text
assistantMessageId 属于 assistantNodeId，角色为 ASSISTANT
anchorMessageId 属于 anchorNodeId，角色为 USER
owner 与 anchor node 都属于 target conversation
expectedSelectedPrefixMessageIds 与锁内 planStartTarget 结果逐项相同
modelContextCandidate 必须是合法 canonical Disclosure envelope
CONTINUE_APPROVAL 不创建 StartTurn，不得替换这些身份
```

`StartTurn` 始终创建新的 Assistant request owner；删除现有 `resume` slot-reuse 分支。审批 / ask-user continuation 只走 `continueActive` 并保留原 `TurnHandle`、owner 和 `TurnRequestContext`；进程恢复只收口旧 Turn，不以新 turnId 复用旧 Assistant message。这样一个 owner message 永远只对应一个 `START` 请求语义。

`ConversationMutation` 增加窄 delta：

```kotlin
val insertedModelContextEntries: List<ConversationModelContextEntry>
val deletedModelContextEntries: List<ConversationModelContextEntry>
```

删除 delta 携带完整条目：按 `(owner_node_id, owner_message_id)` 主键精确删除，不按全局
message id——克隆分支会在其他 Conversation 保留相同 message id。

事务顺序：

```text
header patch
→ deleted variants / nodes and context cleanup
→ node upsert
→ context entry insert-once
→ execution facts
→ artifact references / FTS projection
→ commit
→ Runtime publish
```

DAO 不使用 `@Upsert` 或 replace：首次 key 插入成功；相同 `(owner_node_id, owner_message_id)` key + 相同 row 的命令重放幂等；相同 key + 任何字段不同（content / anchor）明确冲突，绝不覆盖历史。

Draft materialization、普通 append、编辑/regenerate variant 和 Child `START` 都必须遵守同一个命令协议。Snapshot Service 不得直接调用 DAO。

### 12.3 Fail-closed

加载时若出现以下不一致，Conversation 不得伪装 Ready：

```text
context owner / anchor node 不存在
owner / anchor node 不属于同一 target Conversation
owner message 不属于 owner node
owner message 不是 ASSISTANT
anchor message 不属于该 node
anchor message 不是 USER
content envelope type / format 非法
同一 ownerMessageId 出现不同 content
```

数据库 FK 负责 node 级结构删除，Repository mapper 负责 JSON 内 owner/anchor message 与同 Conversation 的语义校验。

## 十三、数据库、Settings、备份与恢复

### 13.1 Room v9 -> v10

`Migration_9_10` 只创建 `conversation_model_context` 和索引：

- 不扫描历史 Conversation；
- 不生成旧会话 Snapshot；
- 不重写 `ConversationEntity`；
- 不重写 `message_node.messages`；
- 不修改 Memory 行；
- 不增加默认 context 行。

旧会话缺少 entry 是合法未初始化状态。第一次新的 `START` 会在新 Assistant owner 下保存当前完整 Snapshot，并指向该请求实际使用的 USER anchor。

需要同步：

```text
APP_DATABASE_VERSION = 10
AppDatabase entities / DAO
DataSourceModule migration registration
app/schemas/.../10.json
Migration_9_10Test
```

### 13.2 Settings / DataStore 保持不变

禁止增加：

```text
Settings.disclosureManualRevision
Settings.modelContextRevision
独立 Preferences revision/token key
Managed/Local source marker
```

原因：

- 它们不是用户配置；
- 会把缓存实现细节泄漏到 `settings.json` 或 DataStore contract；
- 仍不能完整表达恢复、有效配置源切换和默认值变化；
- candidate exact-content comparison 已经足够；
- Snapshot 捕获读取 `SettingsStore.effectiveSettings` 的固定 read snapshot，自然与配置来源解耦。

`SettingsStore` 的 normalize → persist → publish、Local shadow、effective read model 和 managed write rule 均不因本方案改变。

### 13.3 Memory persistence 保持不变

不增加 `MemoryScopeRevisionEntity` 或 `memory_scope_state`。Memory mutation 继续由 `MemoryRepository` / DAO 原 owner 完成；只修正确定性排序。

### 13.4 备份格式保持不变

当前备份使用 `VACUUM INTO` 生成完整 SQLite snapshot，数据库整体作为 `measix_pilot.db` 进入 `rikkahub-durable-v4`。新表会自然随数据库备份，不存在 Conversation/Memory export mapper。([当前配置参考](../references/android-configuration-architecture.md))

因此：

```text
MANIFEST_VERSION 仍为 rikkahub-durable-v4
settings.json 不变
mcp_catalogs.json 不变
durable directory roots 不变
不新增 disclosure 文件
```

恢复 v4 + Room v9 数据库后，由 Room 在应用重新打开数据库时执行 `Migration_9_10`；v10 备份 round-trip 必须保留 context rows。archive manifest 版本和 Room schema 版本是两个独立协议，不能因新增表机械升级 manifest。

### 13.5 旧 active turn

App 升级需要进程重启。既有 `ApplicationRecoveryCoordinator` / `TurnRecovery` 先收口上一进程遗留的非终态执行，再开放新 durable command；不为旧运行增加一条“legacy disclosure continuation”双路径。

新的 context 语义只从迁移后第一次新 `START` 生效。审批继续和 Tool continuation 不在中途初始化 entry。

### 13.6 Content format 演进

`content.format` 是模型上下文协议，不是 Room schema：

- renderer 只生成当前 format；format 改变后，下一次新 `START` 因 bytes 不同自然追加新 entry；
- 已提交 entry 永不后台改写，历史请求继续发送其 exact content；
- loader 至少验证 envelope 的 `type`、整数 `format` 和 canonical JSON 形状；当前 App 只接受它明确支持的 durable formats；
- 未来若停止支持一个已经落库的 format，必须提供显式 Room 数据迁移或产品级历史处置，不能用“解析失败就忽略”作为 fallback；
- section 增减进入同一个聚合 envelope，不增加列、section 表或独立 revision。

## 十四、Fork、删除、压缩与 Child

### 14.1 Fork

Fork 复制目标消息点之前的：

```text
selected message tree / variants
与被复制 node/message 对应的 model-context entries
```

必须显式建立：

```text
oldNodeId -> newNodeId
oldMessageId -> newMessageId（如果 clone 路径重建 message identity）
```

再同时映射 context owner 与 anchor。只有 owner Assistant 和 anchor USER 都被复制、且映射后仍满足统一因果适用谓词的 entry 才能进入 Fork；不得假设 Master 与 Child 的 clone 逻辑永远保留 message ID。

这样 Fork 的历史 baseline 与源分支一致。Fork 后第一次新 `START` 仍捕获当前 live candidate；如果当前状态已不同，会由新的 Assistant owner 在 Fork 尾部追加完整 Snapshot，形成明确的 rebase，而不是篡改历史 entry。

### 14.2 删除与截断

- 删除 node：FK cascade 删除其 entries；
- 删除一个 message variant：Transition 显式删除以它为 owner 或 anchor 的 entries；
- 截断树：删除节点的 entries 一并收口；
- 选择 variant：只改变请求使用的 branch，不复制或重写 entry；
- 损坏 entry 不静默丢弃。

### 14.3 显式压缩

压缩模型请求仍使用压缩前 selected branch 和适用 context entries。压缩成功替换 durable tree 后，被删除 node 的 entries 随 FK 删除；下一次新 `START` 捕获完整 baseline。

不为 Disclosure 增加保留 Tool Result 的例外，也不生成 Delta Snapshot。

### 14.4 Child Conversation

每个 Child 是独立 Conversation，task USER message 是自己的 anchor，Child `START` 创建的 Assistant variant 是 owner：

```text
Target Assistant 的 Memory scope
Target 当前可见的子助手集合
Child task USER message
```

如果 Target policy 不允许 Assistant Tools，子助手 section 使用固定 disabled 形状。Child task USER 先按既有 create/append 协议提交；只有 Child 真正 `START` 时，entry 才与 Child Assistant slot / turn_execution 原子提交。创建了 task 但未开始模型请求时不得伪造 entry。

Parent Context 不因 Child 创建或运行改变。Child clone/fork 必须按自己的 node/message map 复制 entries。

## 十五、缓存影响

| 场景 | 新行为 | 缓存语义 |
| --- | --- | --- |
| 同 Turn Agent 修改 Memory | Snapshot 不变，追加 ToolCall/Result | 既有前缀稳定 |
| 同 Turn Agent 修改子助手 | Snapshot 不变，追加 ToolCall/Result | 既有前缀稳定 |
| 下一次新 `START` live state 已变化 | 由新 Assistant owner 在请求 suffix 位置追加完整 Snapshot | 不重写此前前缀 |
| 下一次新 `START` 内容未变化 | 不新增 entry，复用目标分支最近 baseline | 不增加重复 token |
| regenerate 同一 USER | 新 Assistant owner；按排除旧 owner 后的目标分支判等 | 不复制 USER，也不覆盖旧 entry |
| 日期跨天 | `memory_tool` definition 不变 | 不因日期击穿工具前缀 |
| 历史窗口移动 | 最近窗口 baseline 投影到 retained 起点 | 接受自然裁剪造成的前缀变化 |
| App 升级且 format 变化 | 下一次新 `START` 追加新 format entry | 不重写旧历史 |
| Fork | 复制历史 entries；必要时在新尾部 rebase | 不伪造 fork 点状态 |

OpenAI 当前建议保持工具定义、排序和 Schema 稳定，并以 append-only 方式管理变化；动态内容应尽量位于稳定前缀之后。([OpenAI Docs][1]) Anthropic 的缓存层级是 `tools → system → messages`，修改工具定义会使后续缓存失效。([Claude Platform Docs][3]) Gemini 隐式缓存同样受益于相似前缀。([Google AI for Developers][5])

本方案保证的是：

```text
不因 live disclosure 变化重写已经发送过的历史前缀
```

不是承诺每次命中。Provider 的最小 token、路由、TTL、显式/隐式缓存和模型策略仍决定实际命中。


同一 Turn 修改 Settings、Assistant、Model 或工具启用项时：

- 后续 Provider step 的 System、工具定义、排序、Transformer 与 request shape 逐字不变；

## 二十、最终不变量

1. **Durable Conversation、Conversation Presentation、Model Request Plan 是三个明确概念；任一投影都不能成为第二持久化事实源。**
2. **模型上下文保存在 `conversation_model_context`，不进入 `ConversationEntity` 热行、MessageNode JSON、Settings、FTS 或 UI。**
3. **每个 Snapshot entry 由一次 durable Assistant request variant 拥有，并指向该请求的因果 USER；它只随 `StartTurn` 的 Assistant slot / turn_execution 原子提交。**
4. **Snapshot 只追加，不改写历史 entry；相同 canonical content 不重复写。**
5. **每个新 `START` 都从当前有效读模型捕获 candidate，并对结构变换后的目标分支判等；同一 active Turn 的 step、审批、工具和重试不刷新。**
6. **每个 Turn 只有一份进程内 `TurnRequestContext`；所有影响模型可见 wire 的已解析输入和工具定义同 Turn 冻结，执行权限仍 live fail-closed。**
7. **Agent 与用户修改不需要持久化 mutation origin；变化在下一自然 `START` 边界由完整 Snapshot 吸收。**
8. **后出现的完整 Snapshot 按时间顺序成为新 baseline，不需要 generation 或 effect 协议。**
9. **Provider 请求中 context 是 anchor USER turn 的第一个 model-only part，真实用户 parts 保持完整、同序的 suffix。**
10. **跨协议不依赖相邻 USER；OpenAI、Claude 和 Gemini 都编码一个合法 USER turn。**
11. **System / Developer 只保存稳定规则，不包含动态 Memory 或子助手 Catalog。**
12. **工具名称、描述、Schema 和排序不得包含日期、Memory、Catalog 或其他 live disclosure。**
13. **Snapshot 是模型认知，不是授权；实际执行始终由 live owner fail-closed 校验。**
14. **历史裁剪只由现有 `ConversationContextPlanner` 决定；context baseline 是该 planner 的同一请求投影，不增加例外或第二 planner。**
15. **Room 只做一次 v9→v10 additive migration；Settings、Memory schema 和 `rikkahub-durable-v4` 格式不变。**
16. **Fork、regenerate、variant、删除、压缩和 Child 都按 owner/anchor node/message identity 处理 context，不用 role 或对象身份推断。**
17. **旧动态注入路径在实现交付中物理删除，不保留 facade、fallback、dual read 或兼容白名单。**
