## 工作方法与同步原则

### Git 远程与检查范围

| remote | 用途 |
| --- | --- |
| `origin` | Fork 的日常开发与推送 |
| `upstream` | 原项目，只执行 fetch 和审查，不直接 merge/rebase |

1. 先执行 `git fetch upstream`，从上批冻结终点到本次实际审查终点列出提交；完成记录不得使用会漂移的 `upstream/master`。
2. 用 `git rev-list --count <start>..<end>` 校验提交数，并确认本批起点等于上批终点；若上游重写历史，先记录 hash 映射。
3. 逐提交查看完整 diff，再沿本地入口、application/query port、唯一 writer、取消/失败、恢复、持久化、UI 和测试调用链核对。
4. 同一能力被后续提交修正时，以冻结范围内的最终态为准；包名和品牌差异只做语义映射，不机械搬运。
5. 代码与静态契约测试是实现事实，`docs/references/` 是当前架构参考；冲突时按当前 owner、写协议、持久化聚合和产品边界设计。

### 固定判定

- 原则：必须阅读 `docs/references/` 相关权威参考文档，详细设计必须按我们的架构、结构和规则要求进行合理调整。

| 判定 | 含义 |
| --- | --- |
| **引入** | 本地存在同一缺陷或能力符合产品边界，且上游最终态可直接遵守当前架构 |
| **适配引入/架构重写** | 目标有价值，但上游 owner、协议、品牌或 UI 结构不同；只吸收目标，按本地唯一边界实现 |
| **本地已覆盖** | 当前实现已有等价或更强语义，并有可核对的调用链或测试；不重复同步 |
| **本批不引入** | 无本地可达链/消费者、违反产品边界、来源不可审计，或需另行完成架构设计；详细文档必须记录重审条件 |

依赖、API、持久化与权限变化仍需完成许可证/ABI/兼容性、migration、schema 同构、数据保全或授权时机检查，
再归入上述唯一结论。引入的新行为必须覆盖失败、取消、恢复和竞态；不得以兼容 facade、旁路写入或第二状态源迁移上游实现。

### 文档与完成门槛

- 每批详细文档命名为 `batch-N-YYYY-MM-DD.md`，保存逐提交结论、架构适配、跳过理由、测试矩阵和验证证据。
- 总账只保存冻结范围、状态、极简介绍和详细文档链接；历史内容有修正时修改详细文档及对应索引行，不在总账复制正文。
- 分析完成但未实施的批次标记为 ⏳；只有分类计数闭合、代码落地且风险匹配门禁通过后才能标记为 ✅。
- 稳定检查点另建 `phase-N-review-YYYY-MM-DD.md`，复核范围连续性、产品边界、最终职责、持久化兼容和全量验证；阶段复核不替代逐批记录。
